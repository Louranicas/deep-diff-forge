# DDF-2026-001: a review could show a different result than `git apply` writes (`Files … differ`; one path in several sections)

| | |
| --- | --- |
| Severity | High: two high findings (G1, G2) of the independent assessment of 0.8.3 |
| Affected | Every release up to and including 0.8.3. Measured on 0.8.2 and 0.8.3; for earlier releases inferred from the code, since no commit before the fix reads either shape |
| Fixed in | 0.8.4: the signed tag `v0.8.4` on the GitLab repository of record (`https://gitlab.com/lukeomahoney/deep-diff-forge`) and its mirrors on Gitea and Forgejo |
| Found | 2026-11-12, by the project's independent assessment of the released 0.8.3 binary, with Git 2.56.0 and real applies |
| Published | With the tag `v0.8.4` |

## What went wrong

deep-diff-forge shows a reviewer what a patch does. Two shapes of patch were shown as one thing
while `git apply` wrote another. Both are well-formed patches that `git apply` accepts with exit 0.

1. **`Files … differ` (G1).** Git takes a section with no hunk as binary when the line after its
   header begins `Files ` (as well as `Binary files `) and ends ` differ`. With a full
   `index <old>..<new>` line, `git apply` then writes the blob `<new>` from the repository's
   object store into the file, or empties the file when `<new>` is all zeros. 0.8.3 knew only
   `Binary files `. It showed such a section as `modified` with no hunk and no binary flag, and
   exit 0; with `rename from`/`rename to` it showed `renamed`, and with `new file mode 100755` it
   showed `added` with no content, where Git wrote the stored blob into a new executable.
2. **One path in several sections (G2).** Git applies a patch as a set: every removal first,
   every creation after, and a rename or copy reads its source as it was before the patch.
   0.8.3 showed the sections one after the other. Measured with Git 2.56.0, each exit 0:
   - "modified `x`", then "deleted `x`": Git leaves `x` in place, holding the modified content;
   - "added `x`" (executable), then "deleted `x`": Git leaves the new executable;
   - "modified `.github/workflows/ci.yml`" (a new step), then "renamed" to `docs/ci-example.yml`:
     Git leaves the workflow, with the new step, and gives the docs file the old content;
   - "renamed `x` to `y`", then "renamed `y` to `z`": `y` ends up holding the old `x`;
   - two `new file` sections for one path: Git keeps the second.

## What this could cause

A reviewer, or a gate that reads deep-diff-forge's review, could accept a change that is not
the change shown:

- **G1:** the whole content of a file replaced by any blob already in the repository's object
  store (an older version of the same file that undoes a fix, or a blob from any fetched branch
  or pull request), or the file emptied, while the review showed a change with nothing in it.
  Emptying a file needs only its current blob id. This takes a patch written on purpose:
  `git diff` writes `Binary files … differ` for a binary change, not this shape.
- **G2:** a file left in place, with content the patch chose, where the review's last word on
  that path was "deleted" or "renamed away". Each hunk was shown under its true path; a reader
  who followed the sections in order still reached a different tree than the one Git writes.
  Besides an author who means it, two patches joined into one can make this shape by mistake.

In 0.8.3 no ranking signal marked the shapes themselves: a G1 section had no `binary_change`
signal, and nothing marked a path named by two sections.

## How to check a version

`deep-diff-forge --version` prints the version; 0.8.3 and earlier are affected. A build from a
commit after 0.8.3 but before the tag also says 0.8.3, so check the behaviour, not only the
number. This section is the shape Git calls "patch with only garbage" and writes nothing for; it
is safe to run anywhere:

```bash
printf 'diff --git a/x b/x\nindex 1111111..2222222 100644\n' | deep-diff-forge --stdin-patch --json
```

0.8.3 exits 0 and shows `x` as `modified` with no hunk. 0.8.4 exits 4 ("holds nothing git apply
reads as a patch").

## What 0.8.4 changes

- **`Files … differ` is read as the binary marker**, exactly as `Binary files … differ` is: the
  section has status `binary_changed` (with the `binary_change` signal), under the same rules
  (it ends the header; it is refused straight after `diff --git`, after the section's
  `---`/`+++` and under a submodule mode). Where Git does not read the line as the marker, it
  stays ignored text.
- **A Git section with no hunk and no change in its headers is refused** (exit 4), for example
  an `index` line alone. Sections Git does write with no hunk are still read: a mode change, a
  pure rename or copy, an empty file created or deleted, and a binary section.
- **A path written by two sections, removed by two, or written by one and removed by another is
  refused** (exit 4, error `PathInSeveralSections`, naming the path and the line of the later
  section). Two shapes stay reviewed, each shown by a real `git apply` to give the tree the
  sections describe in order: a change in place after a section that wrote the path (so a
  `git format-patch --stdout` series that changes one file in several commits is still
  reviewed), and a `new file` section after a `deleted file` section for one path (how Git writes
  a change of type). A copy or rename whose source another section changes is a read, not a
  conflict, and stays reviewed: its content is the source as it was before the patch, which is
  what Git copies.
- **A traditional diff with `/dev/null` on both sides is refused** (L1, low, of the same
  assessment): Git created a file named from the whole second line (`dev/null run.sh`) where the
  review showed `dev/null`.
- The project's Git differential test now applies each case for real into a scratch repository
  with a seeded object store, and compares the tree Git writes with the review
  (`crates/deep-diff-forge-patch/tests/git_differential.rs`, module `real_apply`).

## What 0.8.4 does not change

- **A binary section is still shown without its content.** After the fix, the G1 shape is
  shown as `binary_changed`; Git may still write a stored blob for it. Read `binary_changed` as
  "content not shown", whatever the file's name.
- **Some shapes Git writes are now refused:** two renames in which one's new name is the other's
  old name (a swap or a chain, from `git diff -B -M`), and a series in which a later commit
  deletes or renames away a file an earlier commit created or changed. Review those commit by
  commit.
- Still open from the same assessment: a binary deletion, creation or rename is shown with
  status `binary_changed` (G3, medium); after a binary body that Git finds corrupt, Git stops,
  exits 0 and writes none of the later sections, which the review still shows (F1, medium).
- A review is about the patch bytes it is given. deep-diff-forge does not read the repository's
  object store and does not check that a patch is the whole change between two commits.

## Reproduction

The shapes, as the 0.8.4 tests hold them (`@OLD@` and `@NEW@` stand for full blob ids of the
repository the patch is applied to; the tests seed them):

```text
diff --git a/x b/x
index @OLD@..@NEW@ 100644
Files a/x and b/x differ
```

```text
diff --git a/x b/x
index 1111111..2222222 100644
--- a/x
+++ b/x
@@ -1 +1 @@
-a
+b
diff --git a/x b/x
deleted file mode 100644
index 2222222..0000000
--- a/x
+++ /dev/null
@@ -1 +0,0 @@
-b
```

On 0.8.3 the first is shown as `x modified` with no hunk (exit 0), the second as `x modified`
then `x deleted` (exit 0). On 0.8.4 the first is shown as `x binary_changed` and the second is
refused (exit 4).

## What to do

1. Use 0.8.4 from the signed tag `v0.8.4`: its release archive checked against the signed
   `SHA256SUMS` (`scripts/release_local.sh verify`), or a build of the tag.
2. Re-review any change that 0.8.3 or earlier showed with a section of no hunk, or with one
   path in more than one section, if it touched a file that matters.

## Found by

The project's independent assessment of the released 0.8.3 binary (2026-11-12; score 67/100,
G1 and G2 high), which added Git's object store and real applies of several sections to its
oracle. The `Files … differ` line had first been noted, unrated, by the reviewer of the 0.8.3
fix. Earlier advisories of this series: GHSA-gp5v-m67f-gmgp (fixed in 0.8.2) and
GHSA-rq5r-p3g9-phff (fixed in 0.8.3). Details: [CHANGELOG](../../CHANGELOG.md) (0.8.4).
