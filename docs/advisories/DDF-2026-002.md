# DDF-2026-002: code could be hidden from the code-evidence rules (nested comments, long character escapes, comments opened in an earlier hunk of a new file)

| | |
| --- | --- |
| Severity | Not rated by an assessment. A way to hide code from released ranking signals: the patch's paths, hunks and lines were shown as before; the code-evidence signals and the score were not |
| Affected | 0.5.0 to 0.8.3: every release that has code evidence (code evidence came in 0.5.0). Measured on the published 0.8.3 binary |
| Fixed in | 0.8.4: the signed tag `v0.8.4` on the GitLab repository of record (`https://gitlab.com/lukeomahoney/deep-diff-forge`) and its mirrors on Gitea and Forgejo. Two cases stay open; see "What 0.8.4 does not change" |
| Found | 2026-11-14, during review |
| Published | With the tag `v0.8.4` |

## What went wrong

The ranking reads a "code view" of each changed line, in which comments and literals are blank,
and looks for risky tokens in it. In Rust these are the rules `unsafe_added`, `process_spawn` and
`network_fetch`, and `test_removed` on the removed side. Three things made the view blank text
that the compiler reads as code:

1. **Nested block comments (Rust).** Rust block comments nest. The view ended a comment at the
   first `*/`, so after `/* /* */` a `//` cut the rest of the line, where for the compiler the
   comment is still open and the code after its last `*/` runs:
   `/* /* */ // */ let _ = reqwest::blocking::get(u);`
2. **A character literal with an escape longer than one character (Rust).** After `'\x41'`,
   `'\u{1F600}'` or any longer escape the view was one quote out of step. In
   `('\x41','"', "/*")` it took the `"` of `'"'` for the start of a string and the `/*` of the
   real string for a comment that nothing closed; the rest of the hunk was blank.
3. **A comment or string opened in an earlier hunk of a file the patch creates (every language
   with block comments or strings over lines).** Each hunk was read alone and started as code.
   `git apply` accepts a new file written as several hunks (`@@ -0,0 +1,2 @@`, then
   `@@ -2,0 +3,2 @@`) and writes the lines in order. A first hunk that ends with `/*` and a second
   that is `// */ pub fn evil() { std::process::Command::new("sh")… }` compile to a function
   that spawns a process; read alone, the second hunk is a line comment.

## What this could cause

A patch author who means to could add a process spawn, a network fetch or an `unsafe` block that
the ranking does not flag, so the file ranks lower and a reviewer who relies on the signals looks
elsewhere. Measured on the published 0.8.3 binary:

| Case | 0.8.3 | the fix (its reviewed build, commit `07f4fd2`) |
| --- | --- | --- |
| Two calls written plainly (control) | score 9, `process_spawn`, `network_fetch` | the same |
| The same two calls after `/* /* */ // */` | score 2, no signal | score 9, `process_spawn`, `network_fetch` |
| A new file with an `unsafe` block (control) | score 8, `unsafe_added` | the same |
| The same file with `('\x41','"', "/*")` above it | score 4, no `unsafe_added` | score 8, `unsafe_added` |
| A new Rust file in two hunks, the spawn behind a comment opened in hunk 1 | score 4, no evidence | score 8, `process_spawn` |
| The same in JavaScript, with `execSync(` | score 4, no evidence | score 8, `process_spawn` |

Cases 1 and 2 need no unusual patch: a reviewer reading the source sees odd but legal Rust. No
other language was affected by cases 1 and 2: JavaScript and Go comments do not nest.

## How to check a version

`deep-diff-forge --version` prints the version; 0.5.0 to 0.8.3 are affected. To check the
behaviour, rank this patch (`deep-diff-forge --stdin-patch --rank --json`); it adds two calls
behind nested comments to an existing function and is safe to run, since nothing is applied:

```text
diff --git a/src/net.rs b/src/net.rs
--- a/src/net.rs
+++ b/src/net.rs
@@ -1,2 +1,4 @@
 pub fn sync(u: &str) {
+    /* /* */ // */ let _ = reqwest::blocking::get(u);
+    /* /* */ // */ std::process::Command::new("sh").arg("-c").arg(u).status().ok();
 }
```

0.8.3 gives score 2 and no signal; 0.8.4 gives score 9 with `process_spawn` and `network_fetch`.

## What 0.8.4 changes

- **A second reading of Rust, beside the first.** The view of 0.8.3 is kept exactly, and a second
  view that follows the compiler's own lexer token by token is read with it: block comments nest,
  a character literal is read whole whatever its escape, and strings and raw strings end where
  the compiler ends them. Every Rust rule is asked of each view on its own, and what either finds
  is reported once. So for every patch the signals, the score and the listed items of the ranking
  are at least those of 0.8.3; a file's score can be higher, and its place in the ranking can fall
  because another file's score rose.
- **The hunks of a file the patch creates are also read as one text**, in the order of the patch:
  a later hunk is read once more from what the hunks before it left open. This reading has a
  budget of 256 KiB of new-side text per patch, shared by the created files in patch order, and
  stops at a line longer than 512 bytes. It is a further reading, never a replacement: every hunk
  is still read alone as before.
- The lexer reading is held by a fuzz target that compares it with the compiler's lexer
  (`rust_code_view`), by property tests against the reading of 0.8.3, and by corpus cases.

## What 0.8.4 does not change

- **The cross-hunk reading is not a defence against an author who means to hide code.** One line
  over 512 bytes, an earlier created file, or the file's own earlier hunks that use up the budget
  turn it off. Code that an earlier hunk's open comment hides is then found only where its own
  hunk, read alone, shows it. The whole answer is not 0.8.3's: in Rust the second reading still
  reads every hunk and can find more.
- **Hunks of a file that exists are still read each on its own**, as in 0.8.3. A comment or
  string opened in an earlier hunk, or in unchanged text the patch does not show, can still hide
  code in a later hunk; so can one added line inside an existing block comment that closes it,
  adds code and opens it again.
- A shebang first line, which the compiler skips, is read as Rust by both readings.
- No evidence means no token was found, never that a change is safe.
- **Known and not fixed in 0.8.4 (scheduled for 0.9.0):** white space or a line end inside a
  Rust path (`std::process :: Command`) hides `process_spawn` and `network_fetch`, in
  0.8.3 and in 0.8.4.
- **Known and not fixed in 0.8.4 (scheduled for 0.9.0):** one long JavaScript or TypeScript word
  costs time that grows with the square of its length (doubling the word about quadruples the
  time; 200,000 letters took 18 s on 0.8.3), in 0.8.3 and in 0.8.4.

## Reproduction

The patch under "How to check a version" is case 1. Case 2 is the line
`pub const TABLE: (char, char, &str) = ('\x41','"', "/*");` above an `unsafe` block in the same
hunk. Case 3 is a new file whose first hunk ends with `/*` and whose second hunk begins
`// */`, followed by code. The 0.8.4 tests and corpus hold all three
(`fixtures/eval/evidence/rust-code-view-20261114.patch` in the corpus).

## What to do

1. Use 0.8.4 from the signed tag `v0.8.4`: its release archive checked against the signed
   `SHA256SUMS` (`scripts/release_local.sh verify`), or a build of the tag.
2. Do not treat a missing signal as a clean result, in any version. Read changes to Rust files
   that contain nested comments, long character escapes, or a new file split into several hunks
   with care.
