# DDF-2026-003: a process spawn cut across two sections of one path was not found, and one long word or run of secret prefixes cost time quadratic in its length

## What went wrong

**(a) Content cut across two sections of one path.** Release 0.8.4 refuses a path named by more
than one section of a patch, except where Git applies the sections one after the other: a change
in place after a section that wrote the path, and a new file after a deleted file (which begins
the file again). Plain `git apply` applies such sections to one file, in order. The evidence
rules read each section alone, so a construct whose start is in one section and whose end is in
the next was in neither reading. A string opened at the end of the first section and closed at
the start of the second hid what follows it the same way. Release 0.8.3 and earlier accept the
same shapes and read them the same way.

**(b) Time quadratic in the length of one word, or of one run of secret prefixes.** The
JavaScript and TypeScript scanner asks, at every byte after a word byte, whether the word before
it is one after which an expression starts (`return`, `typeof`, `instanceof`, ...); it walked back
over the whole word each time. The secret rule walked to the end of the run of a credential
prefix that repeats inside its own run (`xAKIAAKIA…`) once for each repeat. Doubling the length
about quadruples the time.

## What this could cause

(a) A patch author who means to could add a process spawn that the ranking does not flag, so the
file ranks lower and a reviewer who relies on the signals looks elsewhere. Measured on
2026-11-18 (`--stdin-patch --rank --json`) with the shapes below; "the fix" is the reviewed
0.9.0 candidate binary (`04d82f2e…`, commit `31103f9e`):

| Shape of `src/two.rs` | 0.8.3 | 0.8.4 | the fix |
| --- | --- | --- | --- |
| One section that creates the file with the spawn (control) | `process_spawn` | `process_spawn` | `process_spawn` |
| A creation, then a change in place that closes the string and spawns | no evidence | no evidence | `process_spawn` |
| A change in place, then another that closes the string and spawns | no evidence | no evidence | `process_spawn` |
| A deletion, a creation, then a change in place that closes the string and spawns | no evidence | no evidence | `process_spawn` |
| A deletion, then a creation that holds the whole spawn (control) | `process_spawn` | `process_spawn` | `process_spawn` |

Plain `git apply` (Git 2.56, measured 2026-11-17 in scratch repositories) writes the joined text, spawn included, in every shape. The fix reports the item
on the section that holds its line.

(b) One added line can hold up a review, a hook or a gate that ranks a patch. Measured on
2026-11-18, CPU time of one ranking on a shared host:

| One added line | 0.8.3 | 0.8.4 | the fix |
| --- | --- | --- | --- |
| A JavaScript word of 200,000 letters (`src/a.js`) | 26.4 s | 26.4 s | 0.02 s |
| `x` and `AKIA` 50,000 times (200 KB, any file) | 3.7 s | 3.7 s | 0.01 s |

An earlier measurement of the same word on 0.8.3, on a less loaded host, took 18 s.

## How to check a version

`deep-diff-forge --version` prints the version; 0.8.4 and earlier are affected. To check (a),
rank this patch (`deep-diff-forge --stdin-patch --rank --json`); nothing is applied, so it is safe
to run:

```text
diff --git a/src/two.rs b/src/two.rs
--- a/src/two.rs
+++ b/src/two.rs
@@ -1 +1,3 @@
 // old two
+pub fn help() -> &'static str {
+    let s = "usage:
diff --git a/src/two.rs b/src/two.rs
--- a/src/two.rs
+++ b/src/two.rs
@@ -3,0 +4,2 @@
+  --help"; std::process::Command::new("sh").status().ok(); // "
+    s }
```

0.8.3 and 0.8.4 give both sections score 2 and no evidence; 0.9.0 gives the second section
`process_spawn` at new line 4.

## What 0.9.0 changes

- **The sections of one path that Git applies in order are also read as one file**: a copy of
  the first with the hunks of all of them in patch order, by every reading, those that join hunks
  among them included. Each section's own reading stays, and what the joined reading finds is
  reported on the section that holds its line. A run spends its whole new side from the patch's
  256 KiB bound, in patch order, and is read so only when it fits and has no line longer than
  512 bytes.
- **The scanner reads at most eleven bytes back** from a byte after a word (the longest keyword
  and one more), which gives the same answer for every text, and the secret rule reads at most
  the length its test needs. One rule now holds the class: no check walks from a match to the end
  of its line, or of its run, more than once for the line, and a test of the gate ranks a line of
  2 MiB of each of the 397 triggers the readers know within a bound.

## What 0.9.0 does not change

- **The joined reading has limits.** A run past the 256 KiB bound, or with a line over 512 bytes,
  is read apart again. A later section whose hunks have old lines is joined to the earlier ones
  only where the joins of one file join it. The earlier sections of the old path of a rename or a
  copy are not joined to it. The README lists these under the section rule.
- **It can also report a construct no form of Git writes** (rare): a later section read by its
  old numbers in the coordinates of one file, or after a creation in the order written, can join
  two lines Git keeps apart. Two such shapes are declared false items in the evaluation corpus
  (`evidence/integrated-review-1-20261118`).
- No evidence means no token was found, never that a change is safe.

## Reproduction

The patch under "How to check a version" is the change-then-change shape. The other shapes are
the same lines with the first section written as a creation (`new file mode 100644`,
`@@ -0,0 +1,2 @@`), or preceded by a section that deletes the file. The 0.9.0 tests and corpus
hold them. For (b), a one-line hunk adding `let v = ` and 200,000 letters to a `.js` file, or
`x` followed by `AKIA` 50,000 times to any file.

## What to do

1. Use 0.9.0 from the signed tag `v0.9.0`: its release archive checked against the signed
   `SHA256SUMS` (`scripts/release_local.sh verify`), or a build of the tag.
2. Until then, read a patch that names one path in more than one section as the file Git writes,
   not section by section, and bound the time a gate gives one ranking.

## Found by

(a) was found on 2026-11-17 while the integrity-signals line was integrated with release 0.8.4,
by a measurement of the shapes 0.8.4 accepts (the seventh independent review of that line had
named the class, IR7-H-2). (b) for the JavaScript word was known before 0.8.4 was released
(FINDING-5, listed in DDF-2026-002 as scheduled for 0.9.0); the secret rule's case was found
while it was fixed. Both were measured again on the published 0.8.3 binary and the 0.8.4 release
binary before this advisory was written. Details: [CHANGELOG](../../CHANGELOG.md) (0.9.0).
