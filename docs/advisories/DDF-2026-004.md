# DDF-2026-004: one I/O error or kill during `council import-tuicr --execute` could block a run's decision journal for good, report a recorded decision as refused, or leave a cut-back journal undetected

| | |
| --- | --- |
| Severity | Not rated by an assessment. A loss of availability and of the journal's own tamper evidence after a fault, not an attack: no input to DDF causes it. A same-user process that rewrites the journal was never in the claim |
| Affected | 0.9.0, measured from a fresh process per step with faults injected from outside the process (`ulimit -f`, a read-only directory, `gdb` at system calls). 0.8.3 and 0.8.4 carry the same journal and storage code (read, not measured) |
| Fixed in | 0.10.0. What stays open is under "What 0.10.0 does not change" |
| Found | 2026-11-18, by the deep hardening investigation of 0.9.0 (`FINDINGS.md` sections A and B), after a Codex hardening review named the journal's commit point |
| Published | With the tag `v0.10.0` |

## What went wrong

The decision journal (`<run>/decisions.jsonl`) is append-only and hash-chained; checkpoints in
`<run>/decisions.checkpoints/` record the head after every import, so that a rewritten or
truncated journal is refused. The documents also said "Exit 4 is a refusal, and nothing is
appended." On 0.9.0:

1. **An empty file that refuses for good.** Every create-new artefact was made at its final name
   first and written after. A failed or killed write of a checkpoint left an empty file there;
   every later import of the run, dry runs included, exited 4 ("EOF while parsing a value"), and
   create-new would not replace it. The same writer makes the export ledger, the reports,
   `execution.json` and `qualification.json`: an I/O error on a ledger record made every export
   and import exit 4, and on `qualification.json`, a report or `execution.json` it made
   `council status` and every reviewer's review fail. The message did not name the file.
2. **Exit 4 with the decision appended.** The journal was appended and synced before the
   checkpoint was written. With the checkpoint directory read-only, the import exited 4
   ("Permission denied") although event 1 was in the journal and verified.
3. **A missing checkpoint was never written.** The identical retry then planned no events and
   wrote no checkpoint. Cutting the journal back to event 0 was not detected (exit 0); it was
   detected only after a later, different decision wrote the next checkpoint. If the comment had
   meanwhile been deleted in tuicr, the decision was gone without trace.
4. **No repair for a torn record or a dead process's lock.** A kill or `EFBIG` in the middle of
   the append (reached with `ulimit -f 1`) left bytes after the last newline, and every later
   import said "the last line is incomplete (truncated)" while `council status` read as for a
   clean run. A create-new `decisions.lock` left by a killed import, or left empty by an I/O
   error while it was written, refused every executing import as "locked" until removed by hand.

Interruption points, measured (`gdb` at the system call; one new event per import):

| Point | 0.9.0 | 0.10.0 |
| --- | --- | --- |
| Kill while the lock is written | empty lock file; imports refused as locked | no lock file is written: the lock is a `flock`, released when the process ends |
| Kill before the append | stale lock | nothing recorded; the next import appends once |
| I/O error on the append | clean, exit 4 | clean, exit 4; a part written is cut back |
| Torn record | every import refused | dry run reports it; the next executing import cuts it off and keeps its bytes |
| I/O error on the journal's sync | event recorded, exit 4, the retry never writes the checkpoint | exit 3; the retry writes the checkpoint |
| Kill before the checkpoint | as above, plus a stale lock | the next import writes the checkpoint |
| Kill or I/O error while the checkpoint is written | empty checkpoint; every import refused, dry runs included | the checkpoint is written before the append: nothing recorded, exit 4 (I/O error) or a temporary file the next import removes (kill) |
| I/O error on the checkpoint's sync | consistent, but exit 4 | as the row above |
| Kill at the lock's removal | committed, stale lock | committed; the left file does not block |
| Kill at the answer | consistent | consistent |

## How to check a version

`deep-diff-forge --version` prints the version; 0.9.0 and earlier are affected. On a run, these
show an affected state (a run directory you can change: make a copy first):

- `ls -l <run>/decisions.checkpoints/` lists a file of size 0;
- `council import-tuicr <run> --session <s>` (a dry run) exits 4 with "the last line is
  incomplete" or "EOF while parsing", or `<run>/decisions.lock` exists while no import runs;
- the highest sequence among the checkpoints is lower than the number of lines in
  `<run>/decisions.jsonl` minus one (a head without its checkpoint).

## What 0.10.0 changes

- **Every create-new artefact is all or nothing.** It is written and synced under a temporary
  name in the same directory (`.ddf-tmp.` and a suffix), linked to its name (which fails if the
  name exists), and the directory is synced. On a failure the temporary file is removed and the
  name is untouched; the error names the file. Readers skip a temporary name.
- **The journal's commit point is the synced append**, and what can fail first does: the lock,
  the checkpoint directory, and the new head's checkpoint written and synced under its temporary
  name. A failure before the append is exit 4 and leaves the journal as it was. A failure after
  it is the new council exit **3, `recorded_incomplete`** (`check_environment`,
  `may_be_transient` true): the message names the events recorded and the file not written, and
  the same import run again completes it. This is an addition to the exit-code contract; no
  existing code changes its meaning.
- **Every executing import reconciles first**, under the lock: a head beyond the newest
  checkpoint gets its checkpoint, even when the import plans no events. This heals runs left by
  0.8.3 to 0.9.0 too.
- **Three repairs, announced** on standard error in one line each and reported by a dry run as
  what would be done: a zero-length checkpoint the journal holds is replaced; a torn last record
  no checkpoint names is cut off, its bytes kept beside the journal in
  `decisions.torn-<seq>-<digest>`; leftover temporary checkpoint files are removed.
- **The lock is an advisory `flock`** for the life of the process, as the hooks and the daemon
  take theirs. A lock file left by a dead process, of any version, no longer blocks; two live
  imports still exclude each other.

Journals, checkpoints, ledgers and reports written by 0.8.3 to 0.9.0 load as before.

## What 0.10.0 does not change

- A torn record that a checkpoint names, and a checkpoint with malformed content other than
  none, stay refusals: they are damage to committed data, not an interrupted write.
- A torn last record that held several new events is cut only after the last newline; complete
  events before it stay recorded and are checkpointed by the repair.
- No power-loss test was run; the order of writes and syncs is what is relied on.
- These are local consistency checks, not signatures, as before.
- Temporary files left in other directories (the export ledger, reports, job directories) by a
  kill are skipped by every reader but not removed.

## What to do

1. Use 0.10.0 from the signed tag `v0.10.0`: its release archive checked against the signed
   `SHA256SUMS` (`scripts/release_local.sh verify`), or a build of the tag. Its first executing
   import of an affected run repairs the states above and says so.
2. Before upgrading, on an affected run (copy the run directory first): stop any import; remove a
   `decisions.lock` whose process is gone; if a checkpoint file is empty and the journal holds an
   event at its sequence, remove the empty file; if the journal's last line has no newline, move
   the bytes after the last newline into a file beside it. Then run the same import again; on
   0.9.0 a head without a checkpoint stays unprotected until a later import appends.

## Reproduction

The investigation's scripts drive the public command line with a fresh process per step:
`a1.sh` (read-only checkpoint directory, then the cut back), `a2.sh` (`ulimit -f 1`, with
`SIGXFSZ` ignored and by default), `a3.sh` (a lock left by an I/O error), `a4.sh` (the
interruption points above through `gdb`), and for section B `export.sh` and `review.sh`. The
0.10.0 tests hold the same states: `crates/deep-diff-forge-cli/tests/council_tuicr.rs` (through
the binary) and the fault tests in `crates/deep-diff-forge-review/src/journal.rs` (an I/O error
injected at each step in-process).
