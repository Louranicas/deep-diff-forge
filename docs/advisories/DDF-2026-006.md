## What went wrong

A change read from Git is what `git diff` prints, and `git diff` obeys attributes that the
reviewed repository controls. DDF already ran no filter, external diff or textconv driver of the
repository, but it let Git decide which files are binary. One line `*.rs -diff` makes Git print
every Rust change as a `GIT binary patch`. The line works in a `.gitattributes` that is never
committed or staged (it is no part of the change), in a `.gitattributes` the change adds, in
`.git/info/attributes` (never part of any diff), and in a file the repository's own
`core.attributesFile` names. `* binary` and a `diff=` driver with `binary = true` in the
repository's configuration do the same. With no attribute at all, one NUL byte in a comment makes
Git's content check call the file binary. DDF then saw a binary section: no hunk, no line, so no
code evidence.

## What this could cause

A change that adds a process spawn, a network fetch, a secret or a removed test, in a file Git was
told to hide, ranks as `binary_changed` with score 3 and the one signal `binary_change`, below an
ordinary one-line edit; a hook or a gate that relies on the evidence sees none. Measured on
2026-11-22 (`--rank --json`, scratch repositories, script `table.sh` of the work notes): a Rust
file whose change adds `std::process::Command::new`, in each of the three selections:

## How to check a version

`deep-diff-forge --version` prints the version. In an empty directory (nothing outside it is
written):

```bash
git init -q demo && cd demo
printf 'fn main() {}\n' > m.rs && git add m.rs && git -c user.name=t -c user.email=t@t commit -qm base
printf 'fn main() { std::process::Command::new("sh"); }\n' > m.rs
mkdir -p .git/info && printf '*.rs -diff\n' > .git/info/attributes
deep-diff-forge --git-working-tree --rank --json
```

0.8.2 to 0.9.0 give `m.rs` the status `binary_changed`, score 3 and the signals
`binary_change` only; 0.10.0 gives `modified`, the signals `diff_suppressed` and
`process_spawn`, and `"diff_suppressed": "attribute"`.

## What 0.10.0 changes

- The acquisition as it was stays the first reading. Every change Git gives as binary is asked
  for once more with `--text`, the same selection and flags, limited to its own paths (as
  literal paths, never patterns). When the answer is the same change (status, paths, modes,
  object IDs), as text, valid UTF-8 (NUL bytes included), within what is left of the 64 MiB
  byte budget, and DDF's parser reads it, it replaces the binary section; otherwise, and when Git
  fails, the binary section stands. No attribute is trusted or looked for first, so the cause
  does not matter: any attributes file, a driver, or the content alone.
- A text section and a binary section of one change are two spellings of one result: tests apply
  the reviewed patch with a real `git apply` and compare the bytes, for every selection, an
  addition, a deletion, a rename, an untracked file and a path that reads as a pattern.
- The act is evidence: such a file carries the new signal `diff_suppressed` (+5, class
  security), and `rank.v0` and `git-acquisition.v0` say why: `attribute` when a `diff`
  attribute is unset or names a driver for the path (`git check-attr`), `encoding` when no
  attribute applies and the file is UTF-16 or UTF-32 (a byte order mark on its line 1, or the
  NULs of UTF-16 or UTF-32 between its characters), judged on the new side of the change, or on
  the old side when the change cannot be read as text or deletes the file; else `content`. A consumer that does not know the label
  should hold, which is the right answer for this act.
- The attribute decides the label, not the text reading: a path whose `diff` attribute is unset
  or names a driver carries `diff_suppressed` even where its binary section stands (a byte that
  is not UTF-8, a reading over the budget). A UTF-16 or UTF-32 file carries it with cause
  `encoding` in either case.
- A second reading (or `git check-attr`) cut off by the 120 s limit or the byte budget is no
  answer and fails nothing: the change stays a binary change, the label of an attribute stands,
  and a change no attribute covers carries `diff_suppressed` with cause `unread` instead of
  standing as a silent binary change. Paths are read again in Git's order, each within the
  budget less every other section as it stands, so one large file does not keep the files after
  it from being read; once the limit has run out, every binary change left is `unread`. A Git
  helper that keeps Git's output open after Git exits no longer holds the acquisition past the
  limit.
- A changed file whose name is not UTF-8 is refused with exit 4 (`change_input`), no longer 3
  (`io`, which says "retry"), on the command line.
- An ordinary repository gives the same output as before, byte for byte, and `--stdin-patch`
  is unchanged.

## What 0.10.0 does not change

- **Still unread:** a file whose text cannot be read back (a byte that is not UTF-8, text over
  what is left of the 64 MiB budget) keeps its binary section, so no evidence rule reads it; the
  label says the act and that the text is unread. A UTF-16 or UTF-32 file is labelled
  `encoding` but not decoded: its tokens are not read (one without a mark is read as bytes with
  NULs between them). Without a mark, only text in Latin-1 has the NUL pattern; other scripts
  rely on the mark. A real binary whose new lines mostly have the pattern is labelled too.
- **A file with no `diff` attribute** that is binary to Git for a NUL byte and whose text cannot
  be read back (a real binary, most often) keeps `binary_change` with no `diff_suppressed`. When
  the second reading of such a file is cut off by the limit or the budget, it is labelled
  `unread`: so a large real binary whose text form passes the budget carries a label (+5) that
  0.9.0 did not give it, and the review goes on. A failure of Git itself in a second reading
  (not a cut by DDF's own limits) still leaves the binary section unlabelled. Each binary
  change costs up to two more Git calls (about 8 ms each).
- **The cause is a reading of the working tree's attributes** (`git check-attr` at the
  repository's top level), also for `--git-range`; the label stands whatever the cause.
- **`--stdin-patch`** reviews the patch it is given: a binary section a caller pipes in cannot
  be read again or labelled. **A file pair** (`deep-diff-forge <old> <new>`) runs Git with no
  attributes but still shows a file with a NUL byte as binary. **The hook's judge** makes its
  patch with no attributes, so it reads a hidden file's text and finds the same evidence as a
  Git selection, without `diff_suppressed`.
- **MCP and RPC `review_change`** still answer a file name that is not UTF-8 with code 3.
- Attributes keep every other effect they have on a Git selection (line endings, the user's own
  filters), as documented in [docs/reference/commands.md](../reference/commands.md#review-a-change).
- No evidence means no token was found, never that a change is safe.

## What to do

1. Use 0.10.0 from the signed tag `v0.10.0`: its release archive checked against the signed
   `SHA256SUMS` (`scripts/release_local.sh verify`), or a build of the tag.
2. Until then, and for changes already reviewed from Git with 0.8.2 to 0.9.0, look in the
   reviewed repository for attributes that hide text: `-diff`, `binary` and `diff=` in every
   `.gitattributes` (tracked or not), in `.git/info/attributes` and in the file
   `git config core.attributesFile` names, for example
   `git ls-files -z -co --exclude-standard -- '*.gitattributes' | xargs -0 -r grep -nHE -- '-diff|binary|diff='; f=$(git config core.attributesFile); grep -nHE -- '-diff|binary|diff=' "$(git rev-parse --git-path info/attributes)" ${f:+"$f"}`,
   and read every `binary_changed` source file of such a change with `git diff --text`.
