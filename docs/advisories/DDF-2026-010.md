# DDF-2026-010: a findings gate passed when the reader of its output had gone

| | |
| --- | --- |
| Severity | Not rated by an assessment. A released gate flag failed open: `findings verify --require-findings` and `--require-all` exited 0 instead of 7 when the reader of standard output had closed before the verdict was written, with nothing on standard error. The verdict document itself was right; only the exit code a gate reads was wrong |
| Affected | 0.8.3 to 0.9.0, both flags. Measured on 2026-11-23 on the comparison corpus's binaries of 0.8.3 (`4cafd0ad…`), the 0.8.4 release (`0c93b3ed…`) and 0.9.0 (`5ba0a366…`), three runs each; earlier releases were not measured |
| Fixed in | 0.10.0. What stays open is under "What 0.10.0 does not change" |
| Found | 2026-11-23, by the critics of the 0.10.0 contract design (corrections 2 of the plan of record, point B.2), measured on a frozen 0.10.0-tree binary |
| Published | With the tag `v0.10.0` |

## What went wrong

`findings verify` writes its sealed verdict to standard output and then decides the refusals
its flags ask for: `--require-findings` refuses a findings file that holds none,
`--require-all` refuses any finding refused or over the limit. Every write to standard output
goes through one function that treats a broken pipe (a reader that has gone, as `… | head -c0`
or a supervisor that closed its end) as a clean exit 0, so that `deep-diff-forge … | head` is a
success. When the reader had gone before the verdict was written, the process exited 0 there
and never reached the refusal.

`--require-files` and `--require-hunks` refuse the patch before anything is written, so they
were not affected, on `--stdin-patch`, the Git modes or `findings verify`.

## What this could cause

A gate that runs `findings verify --require-findings` (or `--require-all`) and closes or never
reads the verdict, and decides by the exit code alone, passed an agent that wrote no findings
or whose findings were refused. Measured on 2026-11-23, stdout a pipe whose reader had exited
before the run, three runs per row ("the fix" is the 0.10.0 candidate):

| Flag and input | stdout | 0.8.3 | 0.8.4 | 0.9.0 | the fix |
| --- | --- | --- | --- | --- | --- |
| `--require-findings`, an empty findings file | open | 7 | 7 | 7 | 7 |
| `--require-findings`, an empty findings file | reader gone | **0**, stderr empty | **0**, stderr empty | **0**, stderr empty | 7, the refusal on stderr |
| `--require-all`, a refused finding | open | 7 | 7 | 7 | 7 |
| `--require-all`, a refused finding | reader gone | **0** | **0** | **0** | 7 |
| `--require-files`, a text that is no diff | reader gone | 7 | 7 | 7 | 7 |
| `--require-hunks`, a mode change only | reader gone | 7 | 7 | 7 | 7 |

## How to check a version

`deep-diff-forge --version` prints the version. With an empty findings file `empty.jsonl` and
any patch on standard input, run (nothing is applied, so it is safe):

```text
python3 -c 'import os,subprocess,sys; r,w=os.pipe(); os.close(r); p=subprocess.run(sys.argv[1:], input=b"--- a/x\n+++ b/x\n@@ -1 +1 @@\n-a\n+b\n", stdout=w); print(p.returncode)' deep-diff-forge findings verify --findings empty.jsonl --require-findings
```

0.8.3 to 0.9.0 print 0; 0.10.0 prints 7 and writes
`refused: 0 findings in the findings file (--require-findings)` to standard error.

## What 0.10.0 changes

- `findings verify` decides its refusal before it writes the verdict. A broken pipe while a
  refusal is pending exits 7 with the refusal's line on standard error (none for
  `--require-all`, as with standard output open). With the reader present nothing changes: the
  verdict is written, then the refusal.
- A diagnostic that cannot be written (standard error at `/dev/full` or a closed pipe) is
  dropped and the exit code stays the command's; before, any such write exited 101.

## What 0.10.0 does not change

- One way out for every refusal and every write ("one door") comes with 0.11.0. Until then the
  commands whose exit 7 is not a `--require-*` flag write first and decide after: by reading
  the code, `eval` (a failing case) and `agent doctor` (a chain that is not ready) exit 0 when
  the reader of their output has gone.
- A broken pipe is still a clean exit for every command with no refusal pending, as `… | head`
  needs.

## What to do

1. Use 0.10.0 from the signed tag `v0.10.0`: its release archive checked against the signed
   `SHA256SUMS` (`scripts/release_local.sh verify`), or a build of the tag.
2. Until then, a gate that runs `findings verify --require-findings` or `--require-all` reads
   the verdict to its end (or sends it to a file) before it takes the exit code, so the
   process never meets a closed reader; or it also checks `counts` in the verdict document.

## Found by

The critics of the 0.10.0 contract design measured it on a frozen binary of the 0.10.0 tree
(three of three runs exit 0 with an empty standard error, against exit 7 with standard output
open), and the fix's lane measured the released binaries above before this advisory was
written. Details: [CHANGELOG](../../CHANGELOG.md) (Unreleased, Fixed), plan of record S3.17a.g2.
