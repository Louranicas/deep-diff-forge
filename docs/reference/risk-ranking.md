# Risk ranking

`--rank`, `--cluster`, the cockpit and `rank_patch` share one deterministic, additive score
per file (`crates/deep-diff-forge-graph/src/risk.rs`). Higher means review first.

| Signal | When | Score |
| --- | --- | ---: |
| *(base)* | any reviewable change | +1 |
| *(primary source)* | not a test, config or lockfile | +1 |
| `public_api_surface` | `lib.rs`, `mod.rs`, or an `/api/` path | +5 |
| `large_change` | ≥ 80 changed lines | +3 |
| `deleted_file` · `new_file` | removed · added (a binary section with a `deleted file mode` · `new file mode` header too, beside `binary_change`) | +3 · +2 |
| `many_hunks` | ≥ 5 hunks | +2 |
| `config_or_lockfile` · `binary_change` | `Cargo.toml`, `*.lock`, `*.yaml`, … · binary | +1 · +1 |
| `diff_suppressed` | Git input only (`--git-*`, MCP `review_change`): Git gave a text file's change as binary, by an attribute (`-diff`, `binary`, a `diff=` driver with `binary = true`, in any attributes file Git reads) or a NUL byte, and DDF read it again as text, so the file's code evidence is found too; `"diff_suppressed": "attribute"`, `"content"`, `"encoding"` or `"unread"` says which. It is raised whenever `git check-attr` says the path's `diff` is unset or names a driver, also when the text cannot be read back (the file then stays `binary_changed` with `binary_change`); the cause is `"encoding"` for a UTF-16 or UTF-32 file (a byte order mark on line 1, or the NULs of UTF-16 or UTF-32 between its characters, judged on the new side, or on the old side when the change cannot be read or deletes the file), which is labelled but not decoded (its byte order mark is seen only when the change shows line 1); the cause is `"unread"` when no attribute label covers a binary change and its second reading was cut off by the byte budget or the time limit, failed, or came back as valid UTF-8 and was not used for any reason (it stays `binary_changed`; the review goes on); a binary change stays unlabelled only when its second reading succeeded and is not UTF-8 (since 0.10.0, [DDF-2026-006](../advisories/DDF-2026-006.md); limits in [commands](commands.md#review-a-change)) | +5 |
| `test_only` | under `tests/` or `test/`, `*_test.*`, `*.test.*` | no bonus |
| `hazardous_text` | a changed line holds a bidi control, an invisible or a control character, or the path (or the path a rename or copy leaves) traverses (`..`, absolute) or names `.git` | +3 |
| `symlink_change` | a symlink is created, changed, removed, or made from a file | +3 |
| `executable_bit` | a file becomes executable: a new `100755` file, or a mode change that adds an `x` bit | +2 |
| `generated_or_vendored` | `vendor/`, `node_modules/`, `target/`, `generated/`, `dist/`, `*.min.js`, `*.pb.rs`, `*.pb.go` | base only: no bonuses, but keeps new · deleted · binary · hazards · symlink · executable |

Whoever writes a patch also chooses its paths, so a path can lower a file's score but never zero it. A new file under `generated/` still ranks above a one-line edit elsewhere.

The scan is **lexical** (`"basis": "lexical"` for what is found on one line; `"hunk"` for what is read across the lines of a hunk: a handler and its empty body, and in Rust any construct of the integrity signals whose tokens stand on several lines). For Rust the rules for `panic_path_added`, `trivial_assert`, `stub_added`, `test_skipped` and `test_removed` read the tokens of a hunk across its lines: each side of the hunk (its unchanged lines with its added or its removed lines) is cut into identifiers and single punctuation marks, white space and line ends only separate them, and a construct is evidence when at least one of its tokens is on an added line (for `test_removed`, a removed line), reported on the first such line. There is no parser in the evidence path and these readings have no budgets: the cost of a hunk is its length times the number of its readings: a hunk stands in at most seven texts (itself, the run Git must make of it and its neighbours, the run round 14's rule makes by its old number, and the runs each of its two numbers makes, with those and alone), a side of a text has at most eight readings, and a Rust hunk has one more, as release 0.8.3 read it (two megabytes of any text rank in a few seconds at most. Measured on 2026-11-18 on the release build of the 0.9.0 tree: the slowest of thirty-four hostile units of two to three and a half megabytes takes 2.1 s of CPU (the signals line alone measured 1.4 s, and 0.65 s before its further readings); and for each of the 397 triggers the readers know, a line of 2 MiB of it repeated, and one 2 MiB word ending in it, ranks in 0.3 s at most. No check walks from a match to the end of its line more than once for the line, and a test of the gate holds every trigger to that bound), the answer of these readings for a hunk does not depend on what else the review holds (only on the hunks of its own file that it is read together with; the reading of release 0.8.4, below, carries from hunk to hunk of a created file within a bound that the created files of a patch share), and a view of one hunk (`--hunks --address`) scans that hunk only, or, when the hunk is read together with others of its file, the texts it stands in and no other hunk (so in a file that `git diff -U0` wrote as thousands of hunks of added lines, one reading of the run those hunks make at the end of the file). Memory is linear in the patch. Beside the patch a scan holds one reading of one text at a time (for each line of the text, a copy for each side the line is on), so at most one reading of the longest text of a file, and that is the whole file when its hunks touch or are joined; a test counts the lines it holds (ninth independent review, IR9-L-3: the figure stated before was measured on other shapes and was low); the test counts lines, not memory, and the figures that follow are measured, not held by it. A hunk is not read on the word of its header, and no number in a header decides what is found. What plain `git apply` does with a hunk (Git 2.56.0, run in scratch repositories; the runs are quoted in the tests): it looks for the hunk's old lines, starting at the NEW position and going outward, and puts the hunk at the nearest place that has them; the old position is read for one thing only, 0 or 1, which says the hunk must be at the beginning; and a hunk whose last line is not a context line must match at the end of the file. (Until 2026-11-15 this paragraph said that the old position places a hunk and the new one is never used. It is the other way round; the rule for the top was right and stays.) The top of a file is a hunk whose OLD position is 0, or is 1 and that holds a line of the old file, and the first hunk of a file the patch creates. The weights are the ones the scorer uses, the sides come from the rule table, and a code-evidence label's `basis` lists every rung an item of it can stand on, read from the rules that set an item's (`lexical`, and `hunk` for a handler with its body and for a Rust construct over several lines), so the document cannot disagree with a ranking; a test holds the two tables above to it, and another every item of the evaluation corpus. `deep-diff-forge explain signal <label> [--audience agent|person] [--json]` says why a signal matters, which changes answer it (`accept`), which only hide it (`not_accepted`, each naming the signal that substitute raises, or `null` where none sees it yet), and the compiler or linter rules that stop the construct before a review does (`native_lints`). That is the people's form (`"audience": "person"`, and a last text line `audience: person`): it lists every substitute, including the ones no label raises. `--audience agent` prints what an agent is shown (`"audience": "agent"`): the same reasons, repairs and rules, and of the substitutes only those with an agent sentence, each `{agent, raises}`. A substitute has an agent sentence only when it raises a label and a committed witness patch, `fixtures/diagnostics/witness/<id>.patch`, makes this engine raise that label; each spelling the sentence quotes stands in a changed line of the witness, and a test runs every witness. Every repair and every substitute has an id, `<label>:a<k>` or `<label>:n<k>`, assigned once and never reused or renumbered; `fixtures/diagnostics/ids.v0.txt` pins them. The `--json` form names them beside their entries: `accept_ids`, in the order of `accept`, and `id` in each `not_accepted` entry, for both audiences; the text form does not print them.

Ties break on path, so the order is reproducible. Under `--cluster` the result is
**identical for any worker count**: parallelism never changes the answer.
