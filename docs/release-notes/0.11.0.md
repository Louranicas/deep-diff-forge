# Deep-Diff-Forge 0.11.0 (2026-11-25)

**The agent-loop release.** 0.11.0 is built for an agent that works under Deep-Diff-Forge's
hooks. While it works it is told what its change carries, as items of a new document,
`deep-diff-forge.diagnostics.v0`: one diagnostic for each place a label stands, with the
repairs that answer it, printed by `--diagnostics`, served in pages by the daemon's engine
protocol 3 and by MCP, and read and checked by both SDKs. When it stops, forge-warden's verdict
decides, and the stop judges more than before: the commits an ended session left and the
commits merged between sessions (the project's frontier, kept in a ledger of stops under the
repository's Git directory), the working tree even when the session's state cannot be used, and
each commit with one parent in the judge's bound mode, so that such a commit can pass under a
policy that requires verified claims. Every exit 7 has one meaning and names its reason class;
`agent check` judges on demand what a stop judges, and `agent verify-branch` reads the ledger.
It fixes one miss of released versions with an advisory: `eval` and `agent doctor --gate`
exited 0 when the reader of their output had gone (DDF-2026-011). It closes the miss
DDF-2026-006 declared: a source file that a stray byte makes binary by content is read.

Know four things before installing. The hooks' state is schema v13: the published 0.9.0 and
0.10.0 refuse a session this build has written (UNJUDGED, its files kept), so do not run both
on one session. The Rust readers of four integrity labels and of `check_suppressed` and
`build_hook` read more, and a listed exception to the floor removes two readings (`#[allow(` in
a Rust comment or string, and `r#unsafe`), so a forge-warden policy that forbids these labels
holds more changes and a few others no longer. Under a policy that requires verified claims
only a commit with one parent can pass, and `agent doctor --gate` exits 7 there. The Rust
library API changes where a type gains a variant or a public field. And one limit the review of
this release left stated, under [Known issues](#known-issues): a commit that a session leaves
without a stop can pass the next session's stop under its own edit of the policy, so the judge
on the pull request stays the boundary. Each change on purpose is
under [Changed on purpose from 0.10.0](#changed-on-purpose-from-0100); install it in the order
under [Cutover with forge-warden](#cutover-with-forge-warden), and keep the published 0.10.0
binary as a ranker until every policy admits 0.11.0.

Published as the signed tag `v0.11.0` on GitLab, the place of release, with mirrors on Gitea and
Forgejo and a Linux x86_64 binary built on the owner's machine, with its `RELEASE-MANIFEST.json`
signed beside `SHA256SUMS`; GitHub mirrors the release page and crates.io carries the crates from
the tag, as for 0.10.0.

## Changed on purpose from 0.10.0

What a user of 0.10.0 will see differ, each with the document that states it.

- **A stop judges the project's frontier.** Besides the session's own commits, a stop judges
  every commit after the project's baseline in its ledger that no stop gave a verdict, whichever
  session made it: a commit a session left when it ended before its stop, and a commit merged
  between sessions. Each is marked "(not this session's: left or merged since the project was
  first recorded)", gets the time the session's own work leaves, and a block for one says to
  tell a person and make any repair a new commit. A `SessionStart` with `source` `resume`,
  `compact` or `clear` begins from the commit the last session of its working tree began from
  ([agent hooks](../reference/agent-hooks.md), "The project's frontier").
- **A stop whose state cannot be used judges the tree.** A state that is damaged, newer or older
  than this build reads, a key file that is no key, lists that are not the ones the state names,
  a directory that cannot be used, or a lock another hook holds no longer make a stop say only
  that it did not run. It judges the uncommitted and staged changes without the state, under the
  policy at the ledger's baseline (at `HEAD` with no ledger, which it says): a failing tree
  blocks, stands at the stop that follows a block, and blocks again at the next turn. With a
  baseline it also judges the frontier's commits (not when another hook holds the lock); without
  one it judges no commit
  ([agent hooks](../reference/agent-hooks.md), "A stop whose state cannot be used still judges
  the tree").
- **A commit with one parent can pass under a policy that requires verified claims**
  (forge-warden's `[claims] require_verified`, which its `init` writes from its 0.3.0 line). It
  held before. Such a commit is judged with `--repo`, `--base` and `--head` beside the hook's
  patch when the judge's `check --help` names `--repo`; a judge that refuses bound mode for a
  commit has it judged again without, as before. An uncommitted or staged change, a root commit
  and a merge commit can at best hold ([agent hooks](../reference/agent-hooks.md), "Under a
  policy that requires verified claims, only a commit can pass").
- **A file the hook cannot read, paths marked skip-worktree, and a hold whose only cause is a
  label the judge does not know hold the first stop of a turn once** (owner decision OD-J): again
  when the cause changes, at most three times in a session, never at a stop that follows a
  block; then UNJUDGED, or HOLD, as in 0.10.0 ([agent hooks](../reference/agent-hooks.md),
  "Causes that hold a stop once").
- **The advice after a tool call is an excerpt of the diagnostics document.** Each item is a
  diagnostic for the agent of class `security` or `integrity`, with its code, class, escaped
  path, line, side, case and repair ids as `--diagnostics --json` gives them, then each repair id
  once with its sentence. A `shape` diagnostic (a new or deleted file, a lockfile, a public API
  path, a large change) is no longer advised, and a change that raises only such labels gets no
  advice. An edit of a guard file (the policy, a `.gitattributes`, a CI workflow, lint
  configuration, the client's hook settings) is named once for each content, as information
  ([agent hooks](../reference/agent-hooks.md), the `PostToolUse` row;
  [diagnostics](../reference/diagnostics.md#for-agents-and-for-people)).
- **The hooks' state is schema v13.** A 0.11.0 hook reads a v10 state (written by 0.9.0 and
  0.10.0) and writes it as v13, keeping its base and judged commits; the published 0.9.0 and
  0.10.0 refuse a v13 state as UNJUDGED and keep its files byte for byte. A state of v9 or
  before is refused as older, and a newer one as newer, never written over. Every digest the
  hooks keep is HMAC-SHA-256 under a per-user key file, so a state carried over from 0.10.0 says
  a finding once more and blocks once more for a failure that had blocked
  ([agent hooks](../reference/agent-hooks.md), "The state's schema").
- **What later stops print of a commit from before.** The file of judged commits keeps rule ids
  and reason-class codes only: a later stop names a commit it answered earlier by its rules or
  its class, not by the judge's words (agent hooks, "The state's schema").
- **Engine protocol 3.** `engine.initialize` without `protocol` (or with 3), `engine.methods`,
  `daemon.health` and `daemon.status` report protocol 3 and list the new method
  `diff.diagnostics`; a refusal of another protocol says `this daemon speaks 0 to 3`. Every
  protocol-2 method keeps its params, shapes, codes and messages
  ([the optional daemon](../reference/mcp-sdk-daemon.md#the-optional-daemon)).
- **Exit 7 has one meaning, with reason classes.** Every exit 7 names its class on stderr in one
  line `refused: <text> (<tag>)`; `schema exit-codes`, `explain 7` and MCP's exit-code tools list
  the classes as `refusals` (eleven in this build: the six released refusals and five new ones,
  `fail_on_label`, `fail_on_truncated`, `require_pass_no_unit`, `require_pass_not_pass`,
  `branch_unverified`). A verdict refusal is decided before its document is written, so a closed
  reader or an unwritable stdout still gets exit 7. The texts of `change_input` and
  `review_evidence` are reworded ([refusal reasons](../reference/output-and-exit-codes.md#refusal-reasons-exit-7)).
- **MCP's texts carry no hidden characters.** Every line the MCP server writes, every tool's
  text copy and every error's text writes each bidi control, invisible character, control
  character (but line feed and tab) and line separator as a `\u` escape; `structuredContent` is
  unchanged. A patch that does not parse is refused on every MCP tool with what the engine found
  and the line, and none of the patch's text ([MCP server](../reference/mcp-sdk-daemon.md#mcp-server)).
- **A listed exception to the floor** (owner decision OD-E). `#[allow(` inside a Rust comment or
  a string is no longer `check_suppressed`, in any reading, the ones kept from 0.8.3 and 0.8.4
  included, and `r#unsafe` (an identifier) is no longer `unsafe_added`. On the comparison corpus
  (`fixtures/corpus/compare-v1.sha256`, 7,715 patches) 106 patches lose an item or a label
  against the published 0.10.0, every one of them this exception: 251 items in lists neither
  build cut, each read at its line, and 14 files that lose the label on a list 0.10.0 had cut
  ([risk ranking](../reference/risk-ranking.md#risk-ranking)).
- **Wider readings, no new label.** `check_suppressed` reads `#[expect(..)]`, a conditional
  `cfg_attr` allowance and Cargo's files; `build_hook` reads a build script or procedural macro
  declared in `Cargo.toml`; `trivial_assert`, `error_swallowed`, `panic_path_added` and
  `test_skipped` read more Rust forms. The labels are the 27 of 0.10.0; `tool.scorer_sha256`
  moves ([risk ranking](../reference/risk-ranking.md#risk-ranking)).
- **A traditional section whose one hunk is `@@ -0,0 +1,N @@`** with neither side `/dev/null`
  is `added` with `new_file`, as Git's summary and `git apply` treat it; it was `modified`.

## Known issues

- **Text layouts print a hunk header without its counts:** the inline layout prints
  `@@ -1 +1 @@` for a hunk whose header is `@@ -1,3 +1,4 @@` (the published 0.10.0 the same).
- **The command line's `--json` and `--rank --json`, and the daemon's `diff.compute` and
  `diff.rank`, write a hidden character raw** (a path holding U+202E, for example), where MCP and
  every diagnostics document write it as an escape (the published 0.10.0 the same).
- **A byte order mark is seen only when the change shows line 1:** wide text outside Latin-1
  that is edited elsewhere is not labelled `encoding` (the published 0.10.0 the same).
- **GitHub's own CI** runs on `main` and on pull requests there, not on the release branch: for
  0.10.0 its macOS hook tests failed, and that has not been measured for 0.11.0. GitLab is the
  place of release, and a release commit passes the local gate (`scripts/ci_local.sh`).
- **The hooks' silent and unjudged paths** are the stated limits at the end of
  [the agent hooks reference](../reference/agent-hooks.md); among them:
  - a directory of mode 000, an untracked `.gitignore` that ignores itself and a directory named
    `.git` below the top hide work from Git, and the stop is silent, with no run of the judge;
  - a plain directory at a path the base or the index records as a submodule is listed by no Git
    command: failing work only there gives a silent pass (walking such a path is not built);
  - a very large sparse file makes staging run out of the hook's time: UNJUDGED at every stop
    while it is there, never a block;
  - while a file stays unreadable or skip-worktree marks stay, nothing else of that working tree
    is judged after the first hold, only recorded `unjudged`;
  - a judge that exits while a process it detached from its group holds its output is not read:
    the stop is UNJUDGED when the limit passes.
- **The ledger, the frontier's baseline and the state are kept where the agent can write.** A
  record is evidence that a stop decided so, not proof; an agent that removes or edits the ledger
  is judged as before 0.11.0 (its own range only, said at the stop). The judge on the pull
  request is the boundary.
- **A commit left by a session that ended before its stop is judged under the policy of the
  session that judges it, and can pass under its own policy edit.** The next fresh session
  begins from `HEAD`, which can be the left commit: the whole of its own edit of the policy
  file then applies to it. Where the edit keeps the policy's protection of its own file the
  commit is held; where it also removes that protection, a commit that deletes a rule and
  breaks it passes the stop without a word, is recorded `pass`, and `agent verify-branch`
  verifies it. `agent doctor --gate`'s link `policy_protects_itself` cannot tell under a policy
  that requires verified claims. A session started with `source` `resume` keeps the earlier
  base and fails such a commit. Found by the tree review, stated and not changed in this
  release: the judge on the pull request, which reads the target branch's policy, is the
  boundary ([agent hooks](../reference/agent-hooks.md), "The project's frontier").
- **`agent verify-branch` reads the ledger as records, not as proof.** It refuses a ledger with
  a record that is not whole as its kind is written; it does not check the form or content of
  the digests a stop's record carries, and the ledger has no checksum, so damage that leaves a
  whole record (a commit id changed into another full id) is not seen.
- **One start sentence is untrue in one place:** a session whose state cannot be used is told
  that each stop judges the working tree; in a directory that is no Git repository, or a
  repository with no commit, its stop is UNJUDGED.
- **Under a policy that requires verified claims** an uncommitted or staged change, a root
  commit, a merge commit, and a commit in a shallow clone, with object alternates or with `:` or
  a control character in the Git directory's path can at best hold. `agent doctor --gate` there
  fails its link `claims_verified` and exits 7 also when the judge takes bound mode (measured
  with forge-warden `005a1959` and its starter policy). Bound mode costs about 0.25 seconds a
  commit against 0.09 (forge-warden `005a1959`): 300 small commits after the baseline drain in
  two stops instead of one.
- **A state carried over from 0.10.0, or kept under a key that was replaced, is emptied of its
  digests:** a finding is said once more, a failure that blocked blocks once more and then
  stands, and a cause that holds once begins its count anew (at worst nine holds for one cause
  in a session upgraded from v11 whose key is replaced once, each at a turn's first stop).
- **Where file locks do not keep two hooks of one session apart**, a newer build that writes
  between this hook's reads and its write is not seen, and its state is replaced.
- **A 0.10.0 binary removes no `tmp-r…` scratch directory a killed 0.11.0 hook left:** in a
  repository whose hooks are still 0.10.0 it stays until a 0.11.0 hook or check runs there.
- **Diagnostics propose no edits.** They name the repairs by case; fix operations are parked
  until after 0.11.0, and so are a "resolved" line and a per-session byte budget for the advice.
  The advice's caps per tool call stay: 20 items and about 5,600 bytes.
- **What the diagnostics document does not say:** an empty document never means the change is
  safe; on a patch read from stdin a file given as binary carries no code label, so
  `--fail-on security` passes it; use `--git-*`, or add `binary_change` to the list
  ([diagnostics](../reference/diagnostics.md#what-it-does-not-say)).
- **What stays open of DDF-2026-006:** on a path of no language the readers read, a text drowned
  in stray bytes (more than one in eight) is `binary_change` only; a change Git pairs with
  another as a copy is not read lossily; `--stdin-patch` cannot read a binary section again
  ([DDF-2026-006](../advisories/DDF-2026-006.md)).
- **The Rust library crates keep their API as it is through the 0.x line** (decided in this
  release; [release and publication](../RELEASE_AND_PUBLICATION.md), "The Rust API before 1.0"):
  a public type that carries `#[non_exhaustive]` keeps it and the others stay closed, among them
  `RiskSignal`, `JudgePatchError`, `Coverage`, `Evidence`, `PatchTwin` and `GitChange`; a release
  that adds a variant or a public field says so in its notes; `#[non_exhaustive]` for the rest,
  `Error::source` and the SDK gaps are taken up for 1.0. In 0.11.0 `JudgePatchError` gains a
  variant and `Evidence`, `PatchTwin` and `GitChange` gain public fields, so an exhaustive
  `match` or a struct literal outside the crates must change (Changes, below).
- **Small things the tree review saw and this release does not change:** `agent check` prints an
  empty signal and "(0 items)" for a rule that names no signal; `agent setup --policy` prints a
  hidden character of the policy's name raw in the settings it prints; the `let _ =` reading of
  `error_swallowed` looks at a bounded number of tokens after the call's name, which the
  reference does not state; "[cut here]" in a session's start can fall inside a word;
  `--fail-on` does not take the tag `evidence_truncated` as a value (a cut list refuses
  whatever the list); the hooks' table of guard files does not hold Cargo's `[lints]`, a
  `.cargo/config.toml` below the top or `.github/actions`.
- **Not exercised by the real client sessions of the evidence** (Claude Code, headless, one
  model, one policy): an agent that repairs after a block; a Codex client; an interactive client;
  the user's own settings beside the project's; this program's MCP server inside the client;
  UNJUDGED for any cause but a missing judge; the stateless stop; commits an ended session left
  and commits merged between sessions; a second working tree; `agent check` and
  `agent verify-branch`; the guard notice for `.claude/settings.json`; advice at its caps. The
  contract matrix and the hook tests hold those with stand-in and real judges, without a real
  client ([`EVIDENCE.md`](../../EVIDENCE.md)).
- **Not measured:** a mutation run over what 0.11.0 changed; an independent rescore.
  [`EVIDENCE.md`](../../EVIDENCE.md) says what the gate, the fuzz campaign and the release
  build of the release commit gave.

## Cutover with forge-warden

The stop hook asks forge-warden for a verdict, and forge-warden runs DDF as its ranker. Five
things decide what a stop gets:

- **Hook:** the DDF that runs `agent hook stop`. 0.10.0 reads forge-warden's verdict v2 and v3
  and never starts the judge in bound mode; 0.11.0 reads v2 and v3 and starts a judge whose
  `check --help` names `--repo` in bound mode for each commit with one parent.
- **Judge:** the forge-warden binary, named by its build, since all three print 0.2.1:
  `0.2.1-build` (a build of the release commit of forge-warden 0.2.1, not the published file:
  verdict v2, no bound mode); its hub main `db4c580e` (verdict v3, bound mode); its hub main
  `005a1959` (verdict v3, bound mode, the judge of this release's gate). "forge-warden 0.3.0"
  names its next release line, not a released binary; that line pins the published DDF 0.10.0 as
  its ranker.
- **Vocabulary:** `db4c580e` and `0.2.1-build` do not know six labels DDF 0.10.0 introduced
  (`diff_suppressed`, `error_swallowed`, `panic_path_added`, `stub_added`, `test_skipped`,
  `trivial_assert`); `005a1959` knows them. 0.11.0 adds no label.
- **Policy:** which rankers its `[producer] sha256` admits (the published 0.10.0 binary, this
  release's binary, or both), and whether it requires verified claims (`[claims]
  require_verified`, which the starter policy `forge-warden init` prints at `005a1959` sets).
- **State:** the hooks' state of a running session on disk: v10 (written by 0.9.0 and 0.10.0) or
  v13 (written by 0.11.0).

The rows named are those of `scripts/contract_matrix.sh`, which the local gate's contract-matrix
step runs ([quality gates](../reference/quality-gates.md#quality-gates) lists every row): the
stand-in rows against `scripts/contract-matrix/judge.py`, which answers as forge-warden does, and
the real rows once for each forge-warden recorded by its SHA-256 in
`scripts/contract-matrix/binaries.tsv` (`005a1959`, `db4c580e`, `0.2.1-build`), a row's id
carrying the judge's name. The matrix runs this build's hook; no row runs a 0.10.0 hook against a
judge.

**The procedure.**

1. Before the binary is replaced, copy the published 0.10.0 binary (SHA-256 `121503a8…`, the
   `ranker-0.10.0` row of `binaries.tsv`) into one directory kept for rankers, under a name that
   carries its version (`deep-diff-forge-0.10.0`). Every released ranker a policy still admits
   stays there.
2. Install 0.11.0 and print the hooks with
   `deep-diff-forge agent setup --client claude --hooks --judge PATH --policy NAME --ranker-dir DIR`.
   From 0.11.0 `agent setup` takes the three options and writes them into the session-start and
   stop commands (the judge and the directory by absolute path), and gives the post-tool command
   `--policy`. Replace the hooks of every repository's settings with what it prints: settings
   printed by 0.10.0 give the advice hook no `--policy`.
3. Run `deep-diff-forge agent doctor --gate --judge PATH --policy NAME --ranker-dir DIR` in every
   repository the hooks are registered for, with the values the hooks were printed with. Its
   chain link gives the judge a probe and names the verdict schema the judge wrote; the link
   `claims_verified` says which units can pass. It exits 0 only when every link is ready: under a
   policy that requires verified claims `claims_verified` is not ready and it exits 7 (the start
   of a session names that link as weak and still says stops will be judged), so read the links
   it prints, or `--json`, rather than the exit code alone.
4. Run `deep-diff-forge doctor` on the installed binary: its lines `verdict_schemas_read`,
   `hook_state_schemas_read` and `ledger_version` say what this build reads and writes (verdict
   v2 and v3; hook state v10 to v13, writing v13; ledger 1).
5. Let a running session move up, never down. A session 0.10.0 began is carried over by 0.11.0's
   first hook; a session 0.11.0 has written cannot go back to 0.10.0.
6. When forge-warden policies admit this release's published binary by its SHA-256, the stop
   offers this binary first; until then keep the 0.10.0 binary in the ranker directory. Remove a
   ranker only once every policy admits a newer one.

## Changes

The changelog's entries for 0.11.0, grouped.

### Security

- **`eval` and `agent doctor` name their refusal on stderr and exit 7 when the reader of stdout
  has gone** (F7.h2, [DDF-2026-011](../advisories/DDF-2026-011.md)). `findings verify
  --require-all`, `eval` and `agent doctor` name their refusal on stderr. A verdict refusal is
  decided before its document is written. A stdout that cannot be written at all keeps a pending
  refusal for every class, through the one door (0.10.0 fixed it for `findings verify`).
- **A source file that a stray byte makes binary is read** (S3.27.h, the miss 0.10.0 declared in
  [DDF-2026-006](../advisories/DDF-2026-006.md)). In the Git selections (`--git-range`,
  `--git-staged`, `--git-working-tree`, MCP and RPC `review_change`), when Git's NUL check calls a
  file binary, no attribute applies and the second reading is not UTF-8 but holds at most 128 odd
  bytes per KiB of what it shows (bytes UTF-8 decoding replaces, and controls other than tab,
  carriage return and form feed), that reading, decoded lossily, is read for code evidence beside
  the binary change, which stays (`binary_changed`, `binary_change`); a file it gives evidence
  for also carries `diff_suppressed` with the cause `content`. Real binaries measured hold 329 to
  902 odd bytes per KiB and are read as before; a text drowned in stray bytes (more than one in
  eight) is still read as bytes, its lines unread, but on a path of a language the readers read
  (`.rs`, `.py`, `.sh`, …) every such change carries `diff_suppressed` (`content`) whatever its
  odd bytes. A copy Git gives with its source in one reading is labelled so and not read.
  Library: `PatchTwin` gains the member `stray_text`.
- **MCP writes hidden characters as escapes.** Every line, every tool's text copy and every
  error's text has each bidi control, invisible character, control character (but line feed and
  tab) and line separator written as a `\u` escape. A text copy is JSON and parses to the same
  value as before; `structuredContent` is unchanged; `rank_patch`'s text is the bytes
  `--rank --json` prints with those characters escaped. `max_bytes` counts the answer as written,
  so a view of such text pages earlier and never overflows. Before, every tool but
  `diagnose_patch` wrote U+202E and the like raw.
- **A patch that does not parse is refused without its text** on every MCP tool, by the daemon's
  `diff.diagnostics` and in both SDKs' diagnostics calls: what the engine found, the line of the
  patch and the engine's explanation (`truncated hunk ending at line 5: 1 old / 2 new line(s)
  declared but missing`); a path in such a message is quoted and escaped. Before, MCP's older
  tools quoted the failing line, and the diagnostics surfaces cut the message short. The command
  line and the daemon's protocol-2 methods keep their messages, which quote the line. New:
  `PatchParseError::without_input` (patch crate), `Engine::without_input_in_errors` (daemon
  crate).
- **Nothing the hooks keep holds text from the patch, the judge or Git** (hook state v12, F7.e).
  Every digest they keep (what was said, what was said once, every remembered failure and cause
  that holds once) is HMAC-SHA-256 under a per-user key, `key` in the hooks' state directory (32
  random bytes, mode 0600, read only as a regular file of exactly 32 bytes). The file of judged
  commits keeps rule ids and class codes only, so a later stop names a commit from before by its
  rules or its class, not the judge's words. A copy of a state file without the key confirms no
  guessed line; the key's own reader (the same user, the agent included) still can, so the key
  bounds what a copied file gives away and is not a boundary. A v10 or v11 state is read with
  its base and judged commits; its plain digests are emptied, so a finding is said once more and
  a failure blocks once more. Library: `deep_diff_forge_core::hmac_sha256` and
  `hmac_sha256_hex` (RFC 2104 on the crate's SHA-256, held by RFC 4231).
- **The marks an advice hook leaves under `.git/deep-diff-forge/`** when no state can remember a
  reason are keyed (HMAC-SHA-256 under a key file of that directory); a mark of the old unkeyed
  form is removed when met, and its reason is said once more (F6.b).

- **The daemon and `rpc` speak engine protocol 3** (F5a). The new method `diff.diagnostics`
  (params `patch`, `require_files`, `require_hunks`, `max_bytes`, `cursor`) answers one page of the
  document `--stdin-patch --diagnostics --json` prints: whole diagnostics within `max_bytes` (4096
  to 16777216, counted on the page as emitted), each cut file's entry with its first diagnostic,
  the texts they name, and `page {first, count, total, next_cursor, document_sha256}`, the SHA-256
  of the bytes the command prints; [diagnostics](../reference/diagnostics.md#byte-form) gives the
  byte form exactly. The cursor `dg0.…` belongs to one patch and one engine; a cursor of another
  patch, another engine or outside the document, and a diagnostic that cannot fit `max_bytes`
  with the page header, are refused (-32602) and never cut. In its answer line, bidi controls,
  invisible characters and controls are written as `\u` escapes. `engine.initialize` without
  `protocol` (or with 3), `engine.methods`, `daemon.health` and `daemon.status` report protocol 3
  and list `diff.diagnostics`; with `protocol: 2` it is not listed and is still served. A refusal
  of an unknown protocol now says `this daemon speaks 0 to 3`. Every protocol-2 method is held by a replay of a transcript of
  the published 0.10.0 binary (`tests/protocol_compat.rs`); the replay rule names three kinds of
  difference, the third being values of the build (`daemon.health`'s `retained_bytes` and
  `daemon.metrics`' `engine.peak_retained_bytes`, which a client must not compare across builds).
- **MCP** (F5b): the tool `diagnose_patch` and the `review_change` view `diagnostics`, one page of
  the document each, from the daemon's pager in process, with an output schema. `max_bytes`
  (12,364 to 33,554,432, default 32,768) counts the whole answer as written, both copies.
- **SDKs** (F5b): Rust, the typed model `Diagnostics` (its reader ignores members it does not
  know), `diagnostics(&Review)` in process and `Client::diagnostics`, which pages a protocol-3
  daemon, rebuilds the bytes and checks them against `document_sha256`; Python,
  `diagnostics_patch`, the same. A daemon of protocol 2 is `ProtocolTooOld` and is never worked
  around; pages that break the paging contract end the call with a named error
  (`Error::Document`, `PagingError`); pages that carry a member the SDK does not know end it with
  `UnknownMembers` (upgrade the SDK). Rust's `Error` gains these variants; it is
  `#[non_exhaustive]`. `deep_diff_forge_daemon::change_review` (the acquisition of
  `review.change`) is public.
- **`agent doctor` checks `diagnostics_parity`** (F5c): the probe's diagnostics document from the
  command, the daemon's `diff.diagnostics` and MCP's `diagnose_patch` is one document, compared by
  the SHA-256 of the command's bytes and by the pages' bytes. The local gate has a step of its own
  for this contract (F8.c, 36 steps).
- **`agent setup --client claude --hooks` takes `--judge PATH`, `--policy NAME` and
  `--ranker-dir DIR`** and writes them into the session-start and stop commands it prints (the
  judge and the directory by absolute path; without `--hooks`, a judge that is no file or a

  0.10.0 refused it. `agent --help` lists each form with its own options (D1). `agent setup`
  gives the post-tool hook `--policy` (F6.b).
- **The release notes' commands are run** (D1): a test runs every full command line quoted in
  the release notes of the tree's version and of the newest release on the built binary, and
  fails naming the line of any usage error.
- **Release manifest** (F4.c): `scripts/release_local.sh build` writes `RELEASE-MANIFEST.json`
  beside the archive (listed in `SHA256SUMS`): the version, commit, target, the binary's and the
  archive's SHA-256, the rank, diagnostics and hook-state schemas and the ledger version the
  binary writes, the verdict and hook-state schemas it reads, its engine protocol and methods and
  its `scorer_sha256`, each read from the binary itself with the command named in `sources`. The
  owner signs it with the release key in the namespace `deep-diff-forge-release-manifest`;
  `verify` checks that signature, that every member has a value and that it names the tag's
  commit, version, binary and archive. `deep-diff-forge doctor` prints three more lines:
  `verdict_schemas_read`, `hook_state_schemas_read` and `ledger_version`.
- **Contract matrix** (F4.d): the real rows run once for each forge-warden given (`FW_BIN`, the
  gate's judge, now forge-warden `005a1959`; `FW_BIN_OLDER`: `db4c580e` and a build of the
  release commit of 0.2.1), each recorded by its SHA-256 with a name its row ids carry, and the

- **Library API** (F1.a1, F1.a2, F1.a3, F12.a): `Evidence::read_now`, `RankedFile::floor_only`,

### Changed

- **Exit 7 has one meaning, with a registry of reason classes** (F7.h1, F7.i, F3.e, F11). Every
  exit 7 names its class in one stderr line `refused: <text> (<tag>)`. `schema exit-codes`,
  `explain 7 [--json]` and the MCP tools `explain_exit_code`/`exit_code_registry` list them as
  `refusals`; the registry has eleven classes, `fail_on_label`, `fail_on_truncated`,
  `require_pass_no_unit`, `require_pass_not_pass` and `branch_unverified` among them.
  `change_input` no longer says "or drop the contract that refused it"; `review_evidence` reads
  "read the reason and the evidence the message or the council reported; a person decides what
  changes; rerunning does not change it".
- **Stop hook, changed on purpose (owner decision OD-J): a stop the agent itself can make
  unjudgeable no longer goes through at no cost** (F12.a, F12.b). A file of the working tree the
  hook cannot open (looked for only after staging failed: regular files the index or the
  untracked listing names, never through a link, never waiting) and paths marked skip-worktree
  hold the first stop of a turn once, with a sentence that names the escaped paths and nothing
  of Git's words; they hold again when the file changes, at most three times in a session, and
  never at a stop that follows a block. After that the stop is UNJUDGED as in 0.10.0. A hold
  whose only cause is a label the judge does not know (every rule passed, every note
  `unknown_signal`) holds the stop once, naming the label only when it is one of DDF's own; then
  HOLD as before. A nested repository stays a note: the hook cannot tell whether the session
  made it. The ledger records the classes `work.unreadable`, `work.skip_worktree` and
  `hold.version_gap`, and a fail that stands as `fail_stands` (F12.c). `agent doctor --gate`
  says "a stop here would hold once, then be UNJUDGED". Library: `JudgePatchError` gains the
  variant `Unreadable { paths, whole, error }` (the enum is not `#[non_exhaustive]`: a match
  outside the crate that names every variant needs an arm).
- **Stop hook, changed on purpose: a stop whose session state cannot be used** (damaged, newer,
  older, its directory, its key file, its lists, its lock held by another hook) no longer says
  only that it did not run. It judges the working tree without the state, reading and writing
  nothing of the state directory, under the policy at the ledger's baseline (at `HEAD` with no
  ledger, which it says): a failing tree blocks, stands at the stop that follows a block, and
  blocks again at the next turn's stop. With the ledger's baseline it then judges the frontier's
  commits, this session's own among them, each once; without a baseline, or when another hook
  holds the lock, no commit is judged by it. The ledger records it. The start of such a session
  says so: "this session's state cannot be used, so no advice will be given and each stop judges
  the working tree without the session's memory" (F12.d, owner decision OD-J).
- **Stop hook, changed on purpose: a commit can pass under a policy that requires verified
  claims** (S3.25.b; forge-warden's `[claims] require_verified`, which its `init` writes from
  0.3.0); it held before. A commit with one parent is judged with `--repo <the repository's Git
  common directory> --base <its parent> --head <it>` beside the hook's patch when the judge's
  `check --help` names `--repo` (read once a stop; the released forge-warden 0.2.1 does not, and
  is started as before). A pass or a hold whose `seals.claims` are not verified and the asked
  pair is UNJUDGED (`chain.not_a_verdict`). A judge that refuses bound mode for a commit (exit 3
  or 4) has it judged again without `--repo`, and the message says so. A root commit, a merge
  commit, the staged and the uncommitted change, and a repository bound mode does not admit
  (shallow, object alternates, `:` or a control character in its path) are judged as before and
  can at best hold. The stateless stop, the frontier's commits and `agent check` judge commits
  the same way. `agent doctor --gate`'s link `claims_verified` says which units can pass. Cost
  measured with forge-warden `005a1959`: about 0.25 seconds a commit against 0.09; 300 commits
  drain in two stops instead of one. No state or ledger schema changes.
- **Hook state** (F7.e, F6.b). The schema is read strictly (`deep-diff-forge.hook-state.v<N>`),
  from the last release's (v10, written by 0.9.0 and 0.10.0) to this build's own (v13), through
  every migration step, keeping every member: a session started under 0.10.0 keeps its base, what
  has blocked and its judged commits. v11 marks the lines in `blocked` of a cause that holds once,
  which 0.10.0 misread; v12 keys the digests; v13 adds `guards`. The published 0.10.0 and 0.9.0
  refuse a session this build has written (UNJUDGED, file kept), so do not run both on one
  session. An older state (v9 and before) is refused by its name; a newer one by its name and
  the range this build reads, and its message advises no removal. A newer state is never written
  over: the file is read again before the lists and before the state is moved into place (where
  file locks do not keep two hooks apart, a newer build that writes between that read and the
  write is not seen). The refusals of an older or damaged state, and of a list beside it, say
  what removing or starting anew costs. Fixtures written by the published 0.9.0 and 0.10.0
  binaries, and by this build, are read by a test; `scripts/capture_hook_state.sh` captures them.
- **The advice after a tool call is an excerpt of the diagnostics document** (F6.a). Each item is
  a diagnostic for the agent of class `security` or `integrity`, with its code, class, escaped
  path, line, side, case and repair ids as `--diagnostics --json` gives them for the same tree,
  then each repair id once with its sentence. Where the engine cannot tell a case, every repair
  is listed with a sentence saying so. The item text changed (`- "a.rs":2: check_suppressed@line
  (integrity, new side, read as lexical); repairs: check_suppressed:a1, check_suppressed:a2.`). A
  `shape` diagnostic is no longer advised or counted, and a change that raises only such labels
  gets no advice after a tool call: it orders a person's review, and advice that said there was
  nothing to repair after every added file taught an agent to skip the advice. A `floor_only`
  reading is not advised either. A file whose name this version cannot read (not UTF-8) no longer
  turns the advice off for the session: it is one item naming it as Git quoted it, and the other
  files are advised. A change not ranked in the advice hook's time is said once to be "advice cut
  short". [The agent hooks reference](../reference/agent-hooks.md) states what the advice never
  notices (ignored files, `.git/info/exclude`, `.git/info/attributes`, `.git/config`), that the
  advice's `--policy` can differ from the stop's, that guard notices wait for a call that ranks,
  and that a damaged marks key silences the advice beside the state but not a stop (F6.c).
- **`check_suppressed` and `build_hook` read more** (F2b). `check_suppressed` reads
  `#[expect(..)]` and `#![expect(..)]`, with a reason or without, as it reads `#[allow(..)]`; an
  allowance a conditional attribute applies, `#[cfg_attr(condition, allow(..))]` and
  `expect(..)`, through a nested `cfg_attr` too, when the side holds the attribute whole; and
  Cargo's files: in `Cargo.toml` a key whose value is the string `allow` (any TOML quoting, and
  the `level` of an inline table of `[lints]`), and in Cargo's configuration
  (`.cargo/config.toml`, `.cargo/config`) `-A`, `--allow` or `--cap-lints allow` among compiler
  flags. Not read: a string over lines, `clippy.toml`, `RUSTFLAGS` set in a CI file. `build_hook`
  reads a build script or a procedural macro declared in `Cargo.toml` (`build = "…"`,
  `proc-macro = true`) beside `build.rs` itself.
- **Changed, by owner decision OD-E** (the listed floor exceptions to "nothing scores lower than
  0.8.3"): `#[allow(` in a Rust comment or string is no longer `check_suppressed` in any reading,
  the ones kept from 0.8.3 and 0.8.4 included, and `r#unsafe` (an identifier) is no longer
  `unsafe_added`. On the comparison corpus 478 such rows and 3 `r#unsafe` rows are no longer
  reported, counted over every evidence list, cut or not, and 116 files lose the label (113
  `check_suppressed`, 3 `unsafe_added`); in lists neither build cut that is 251 items on 95
  patches, each read at its line; nothing outside the two exceptions is lost. A forge-warden
  policy that forbids
  `check_suppressed` holds more changes (the new readings) and no longer holds one whose only
  `#[allow(` is in a comment or string (F2b.g).
- **Rust readers widened, no new label** (F2a): more lines carry four labels, and a forge-warden
  policy that forbids one holds more changes. `trivial_assert`: an assertion that cannot fail
  read as a class (`assert!(!false)`, `assert!(1 == 1)`, `assert!(true || x)`, `assert!(x == x)`,
  `assert_eq!(x, x)`, `assert_ne!(1, 2)`); the same call on both sides is not read (it checks
  that code is deterministic). `error_swallowed`: `let _ = …;` and `_ = …;` whose last call is
  one of 29 standard calls that return a `Result` (`remove_file`, `write_all`, `send`, `join`,
  `kill`, `wait`, …; `join` and `wait` with no argument, `copy` with two, so that `Path::join`,
  `Condvar::wait` and `ptr::copy` are not read); `write!` into a `String` and the patch's own
  functions are not read. `panic_path_added`: `panic!(…)` and `unreachable!(…)`. `test_skipped`:
  a test compiled out by `#[cfg(…)]` whose predicate is false in every default build of the tests
  (`any()`, `not(test)`, `FALSE`, `feature = "…"`; `not(<a cfg of the build's own>)` holds), and
  by the same predicate a module of tests (`mod tests`, `#[cfg(any())]` before it or
  `#![cfg(any())]` as its first item) or a file of tests by its path (`#![cfg(…)]`). On the
  comparison corpus (7,421 patches) against the tree before: +90 `trivial_assert`, +669
  `error_swallowed`, +778 `panic_path_added`, +47 `test_skipped` rows; no label is lost; in files
  whose evidence list is cut at 32 rows some earlier rows give their place to new ones. On call
  rows of `panic_path_added` the diagnostics member `"cases": ["call"]` is new. Library:
  `deep_diff_forge_graph::Evidence` gains the public member `panic_forms` (a new enum
  `evidence::PanicForms`); code that builds an `Evidence` with a struct literal no longer
  compiles until it names the member.
- **`tool.scorer_sha256` moves** with the readings above (F1.a1, F1.a2, F1.a3, F2a, F2b); the
  first three moves change no label, row or score.
- **A traditional section with neither side `/dev/null` whose one hunk is `@@ -0,0 +1,N @@` is
  `added` with `new_file`** (S3.4.b2): Git's summary and `git apply` treat it as a creation; it
  was `modified`. The deletion twin (`@@ -1,N +0,0 @@`) stays `modified`. On the comparison
  corpus one patch changes (`modified` 2 to `added` 4).
- **The evaluation corpus has 73 cases** (D1, F2a.e, S3.35.d, S3.34.c, S3.34.d; tests and
  evaluation only, no change to what the program does): paired cases (a form read, a near miss
  not read) for every integrity form the Python, JavaScript and Go readers read, and the 46 forms
  a reviewer would expect that no reader reads are cases too, each a declared miss (precision
  233/258, recall 233/360 from 233/314, the denominator grown by the declared misses alone). The
  recall and precision floors are what is measured, and a new floor holds the count of expected
  items found (233), so that a larger denominator cannot hide a lost item. Every missed mutant of
  the 0.10.0 mutation run has a test that fails on it but one, shown equivalent on the comparison
  corpus; `docs/TESTING_GOLD_STANDARD.md` says which functions `cargo mutants` does not mutate.
  The risk-ranking reference states F2b's readings of `check_suppressed`, `build_hook` and
  `unsafe_added` and what they do not read.
