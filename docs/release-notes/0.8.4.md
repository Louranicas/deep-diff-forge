# Deep-Diff-Forge 0.8.4 (2026-11-16)

**Security release.** v0.8.3 and earlier could review a patch otherwise than `git apply`
writes it: a `Files … differ` line, which Git reads as a binary marker and answers with a
blob from its object store, and one path in several sections, which Git applies as a set
(independent rescore of v0.8.3, G1 and G2, high; L1, low). They also hid Rust code after a
nested block comment, after a character literal with a long escape, or after a comment or
a string that an earlier hunk of a created file opened, from every rule that reads Rust
code (found 2026-11-14). Upgrade from 0.8.3; the one breaking change is a new
`PatchParseError` variant (the enum is `#[non_exhaustive]`). G3 of the same rescore
(medium) and the known limits listed under 0.8.3 are not fixed here. This release has no
GitHub release: it is published as a signed tag on GitLab, Gitea and Forgejo; binaries built locally for Linux x86_64.

### Security

- **`Files … differ` is the binary marker `Binary files … differ` is** (independent rescore of
  v0.8.3, G1, high). Git takes a section with no hunk as binary when the first line after its
  header ends ` differ` and begins `Binary files ` or `Files `; with a full
  `index <old>..<new>` line it then writes blob `<new>` from its object store, or empties the
  file when `<new>` is the null id. DDF knew only `Binary files `. `diff --git a/x b/x`, a
  full `index` line, then `Files a/x and b/x differ` was reviewed as `modified` with no hunk
  and no binary flag (exit 0), while `git apply` replaced the whole of `x` with a blob already
  in the store; with `rename from`/`rename to` the review showed `renamed`, and with
  `new file mode 100755` `added` with no content, where Git wrote the blob. Measured on v0.8.3
  with Git 2.56; v0.8.2 is the same. The line is now read exactly as `Binary files … differ`
  is (status `binary_changed`), under the same rules: it ends the header, it is refused
  straight after `diff --git`, after the section's `---`/`+++` and under a submodule mode.
  In the ranking, a binary section with a `new file mode` header carries `new_file` beside
  `binary_change`, and one with a `deleted file mode` header `deleted_file`, with the weights
  of a text file, so a creation or deletion that 0.8.3 ranked as `added` or `deleted` ranks no
  lower (review of 0.8.4, R84-M-1: without it `new file mode 100755` and
  `Files /dev/null and b/n differ` scored 5 where 0.8.3 scored 6). These are the headers Git
  acts on: with one, `git apply` creates or deletes the file, or refuses when the path's state
  disagrees. The names on the binary line are not read for it, as Git does not read them
  (`/dev/null` there, with no mode header, gives neither signal). The status stays
  `binary_changed` (G3).
  Where Git does not read it as the marker it stays ignored text, as measured: after a hunk,
  after a line that already ended the header, and with a carriage return before its line
  feed.
- **A Git section with no hunk and no change in its headers is refused** (G1, the same
  rescore). A `diff --git` section whose only header is an `index` line (or a similarity
  line, or `---`/`+++` names that differ with no `rename` header) is "patch with only garbage"
  to `git apply`, which writes nothing. v0.8.3 and earlier reviewed it as `modified` with
  nothing in it, which is what let an unread line after it go unseen. It is now refused
  (exit 4). The sections Git writes with no hunk are still read: a mode change, a pure rename
  or copy, an empty file created or deleted (with or without its `index` line), and a binary
  section.
- **One path in several sections is refused, except in two section shapes that Git can apply
  in order when their hunks apply** (rescore G2, high). Git applies a patch as a set: every removal first, every creation
  after, and a rename or copy reads its source as it was before the patch. DDF showed the
  sections as a sequence. Measured on v0.8.3 with Git 2.56, each exit 0 on both sides:
  - "modified `x`", then "deleted `x`": Git leaves `x` in place holding the modified content;
  - "added `x`" (executable), then "deleted `x`": Git leaves the new executable;
  - "modified `.github/workflows/ci.yml`", then "renamed" it to `docs/ci-example.yml`: Git
    leaves the workflow with the change and gives the docs file the old content;
  - "renamed `x` to `y`", then "renamed `y` to `z`": `y` ends up holding the old `x`;
  - two `new file` sections for one path: Git keeps the second.

  A patch is now refused (exit 4, new error `PathInSeveralSections`, naming the path and the
  line of the later section) when one path is written by two sections, removed by two, or
  written by one and removed by another. Git sections, traditional sections and binary
  sections are held to it alike. Two shapes stay reviewed, each shown by a real `git apply` to
  give the tree the sections describe in order:
  - a change in place (hunks, a mode change, a binary change) after a section that wrote the
    path, whether that created it, changed it, or renamed or copied a file to it. Git patches
    the earlier section's result, so a `git format-patch --stdout` series that touches a file
    in several commits is still reviewed when no line of its commit messages begins with `-`
    or `+` (`---` included); a series with such a line is refused (a body line outside any
    hunk), as by 0.8.3;
  - a `new file` section after a `deleted file` section for one path, which is how Git writes
    a change of type (a file that becomes a symlink).

  Reading a path is no conflict: a copy whose source another section changes or renames
  away, as `git diff -C` writes it, is still reviewed, and its hunks are against the source
  as it was before the patch, which is what Git copies. Every other pairing on one path is
  refused, and so are some shapes Git writes. These were found; the list is of shapes found,
  not proved complete: two renames in which one's new name is the other's old name (a swap
  or a chain, from `git diff -B -M`); a series in which a later commit deletes or renames
  away a file an earlier commit of the same series created or changed (`git apply` of the
  whole series does not give the series' result there either; `git am` applies it mail by
  mail); a rename of `x` to `y` followed by a new `x` (`git format-patch -M` of a move and
  then a new file at the old name); a deletion of `y` followed by a rename of `x` to `y` (a
  series that removes `y` and then moves `x` there); and a copy onto `x` followed by a
  rename of `x` to `y` (`git diff -B -M -C --find-copies-harder`). For the last three one
  `git apply` gives the series' or the commit's tree; they are refused all the same.
- **A traditional diff with `/dev/null` on both sides is refused** (rescore L1, low). Git
  takes it for a new file and reads the name from the whole second line, so
  `+++ /dev/null run.sh` created `dev/null run.sh` while the review showed `dev/null`. No
  tool writes the pair.

- **Rust code after a nested block comment, or after a character literal with a long escape,
  was hidden from every rule that reads Rust code** (found 2026-11-14; both reproduced on the
  published v0.8.3 binary, each with a control). The Rust rules for `unsafe_added`,
  `process_spawn` and `network_fetch`, and for `test_removed` on the removed side, read a
  view of each line in which comments and literals are blank. That view misread two things
  the compiler reads plainly, and what it took for a comment or a string left no evidence.
  - *Block comments.* Rust nests them. The view ended a comment at the first `*/`, so after
    `/* /* */` a `//` cut the line where, for the compiler, the comment is still open and the
    code behind its last `*/` runs. Measured on the published v0.8.3 binary: a patch that
    adds `/* /* */ // */ let _ = reqwest::blocking::get(u);` and
    `/* /* */ // */ std::process::Command::new("sh").arg("-c").arg(u).status().ok();` to a
    function scored 2 with no signal; the same two calls written plainly scored 9 with
    `process_spawn` and `network_fetch`.
  - *Character literals.* The view knew a literal by a closing quote two bytes on, or three
    after a backslash. After `'\x41'`, `'\u{1F600}'` or any longer escape it was one quote
    out of step: in `('\x41','"', "/*")` it took the `"` of `'"'` for the start of a string
    and the `/*` of the real string for a comment that nothing closed, and the rest of the
    hunk was blank. Measured on the published v0.8.3 binary: a new file with that line and an
    `unsafe` block under it scored 4 with no `unsafe_added`; the same file without the line
    scored 8 with it.
  - *Since when.* Both readings are as old as the view: every release that has code
    evidence, 0.5.0 to 0.8.3. Other languages are not affected: JavaScript and Go comments
    do not nest, and Go's rune literals (`'\x41'`, `'"'`) are read as quoted strings by the
    shared scanner, which finds the code after them.
  - *The fix: a second reading of Rust, beside the first.* The view of 0.8.3 is kept exactly
    as it was, and a second view is read with it. Every rule that reads Rust code is asked
    of each view on its own, and what either finds is reported once. The two are never
    merged into one view, so a token must stand whole in one reading.
    - *The reading of 0.8.3.* The shared scanner reads Rust as every release from 0.5.0 to
      0.8.3 read it (its code is the released code: `lexical.rs` differs from 0.8.3's by
      added lines only), and it carries its own state down a hunk.
    - *The lexer reading.* It follows the compiler's lexer (`rustc_lexer`) token by token,
      with that lexer's rule for where each token ends: block comments nest, to any depth
      and over lines; a character or byte literal is read whole, whatever its escape; a `'`
      before a name is a lifetime or a label; strings, byte strings and C strings, and raw
      strings with any number of `#`, end where the lexer ends them, on one line or over
      several; `r#fn` is a name, and no other letter before a `#` makes one (`k#fn` is `k`,
      `#` and `fn`, as rustc 1.99.1 reads it before edition 2021; the lexer's newer
      `k#name` token is in no edition of that compiler and is not followed); a literal's
      suffix and a number take the letters that belong to them, so an `r` or a `b` before a
      quote is a prefix only where the lexer says so; names past ASCII are read with the
      lexer's own tables (Unicode 18.0.0). Where an edition decides, it takes edition 2021
      and later (`cr"\"` is a raw C string, `'r#name` a raw lifetime). What the lexer calls
      unterminated, and what it closes as a character literal that no compiler accepts
      (`'ab'`, one over a line end), is passed over whole and kept as text. Once a string
      has run over a line end, the lines after it are read both ways inside this reading,
      and the one that resumes every such string, the compiler's for text that starts in
      code, is kept apart and never dropped.
    - Python, JavaScript and TypeScript, Go, shell and YAML have one reading, exactly as
      before.
  - *In the ranking, nothing 0.8.3 found is missing, by construction and by test.* The first
    reading is 0.8.3's own, so every item 0.8.3 reports for a patch is reported, and every
    file's score is at least what it was (each signal found adds a weight of at least 1).
    This is why the old reading stays: where a hunk starts inside a string or a comment
    opened above it, neither reading is the compiler's, and each finds code the other does
    not. Measured: a
    function added below a list kept in a string that holds `crates/*/*/Cargo.toml` (to a
    reader that starts in code: `/*`, `/*`, `*/`) scores 6 with `process_spawn` in the
    reading of 0.8.3 and 2 with nothing in the lexer reading alone, and `git diff` writes
    that hunk. Held three ways:
    - a property test in the gate: for 4,000 generated Rust hunks (as a new file, as added
      lines, as removed lines and as a mix), the items found are those the reading of 0.8.3
      finds alone together with those the lexer reading finds alone, no fewer and no more;
    - a rule in the `evidence_scan` fuzz target: a rule token the reading of 0.8.3 shows on
      a changed line of a Rust file is evidence;
    - a comparison with the published v0.8.3 binary on 3,094 patch files (the patches of
      this repository's commits, its fixture patches and the reproduction patches collected
      while this change was reviewed) and on 300,000 generated Rust hunks and new files: no
      score is lower, no signal and no item is missing.

    The printed list of a file's items has a bound of 32, as before, and the bound could
    have cost an item: one that only the lexer reading finds, early in a file, would have
    pushed the last of 32 items 0.8.3 listed off the end. So at the bound the list holds
    first the items the reading of 0.8.3 finds, as many as fit, and then, in the room that
    is left, items only the lexer reading finds; the items listed stay in the order of the
    file. With 32 or more items of the first kind it is exactly the list 0.8.3 printed, and
    it never holds fewer of them. The score and the signals count every item, and
    `evidence_truncated` says when the list is not all there is. Measured on the published
    v0.8.3 binary: a fetch behind a nested comment on line 1 and 32 process spawns below it
    list the spawns on lines 2 to 33 there (score 8) and here (score 11, with
    `network_fetch` among the signals); and of 12,000 large generated Rust files, 5,376 of
    them with a list cut at the bound, none lacks an item v0.8.3 lists (without this rule
    3,162 did). Held by a rank test, the same at the JSON level, a
    property test (400 generated files of 40 to 120 changed lines: the list 0.8.3 would
    print is contained in the list printed) and a rule of the `evidence_scan` fuzz target.

    So the claim is this, and no more: for every patch, the signals, the score and the
    listed items (at the bound of 32 a file) of the ranking are at least those of 0.8.3. An
    answer that is bounded in bytes (the MCP summary, a protocol line, a page) reaches its
    bound sooner when it says more, and says so as before (a summary with its omitted count,
    error 8, a cursor); time and memory are linear in the patch, within the factors stated
    (the next entry has the measurements). Three cases measured against the published v0.8.3
    binary (second independent review, 2026-11-15):
    - *The MCP summary.* `rank_patch` answers a ranking over 256 KiB with
      `rank-summary.v0`, the highest-ranked files that fit. For a patch of 1,500 small Rust
      files, one of which has fetches only the lexer reading finds, 0.8.3 lists 1,094 files
      (`omitted_files` 406) and this build 1,082 (418): twelve files 0.8.3 listed, with their
      items, are among the omitted. And a ranking that is 147 bytes under the cap on 0.8.3
      (1,096 files, answered whole) is over it here and comes back as a summary of 1,094.
    - *A protocol line.* An answer over the 80 MiB line cap is error 8. A `diff.rank` answer
      of 83,885,992 bytes on 0.8.3 (115,864 files; constructed to stand under the cap by a
      few hundred bytes) is 83,886,151 bytes here, and so error 8.
    - *A page.* The first page of `--outline` (64 KiB unless asked otherwise) for a new Rust
      file of 313 one-line hunks holds all 313 on 0.8.3; here it holds 312 and a cursor,
      because 150 of the hunks now carry a label. Nothing is lost to a reader that follows
      the cursor.

    `--rank --json` on the command line has no bound in bytes. Nothing was built for these
    three bounds: a count could be filled with the items of 0.8.3 first, bytes cannot.
  - *How the lexer reading is held.* A new fuzz target, `rust_code_view` (the eleventh),
    compares it with the compiler's lexer itself (`ra-ap-rustc_lexer` 0.184.0, a dependency
    of the fuzz crate only, never of a crate that ships: the fuzz lock gains it and
    `unicode-properties` 0.1.5 and moves `unicode-ident` from 1.0.24 to 1.0.27, the Unicode
    18.0.0 tables that lexer needs; the workspace lock and the SBOM do not change), read as
    rustc 1.99.1 reads it where that lexer is newer (its `k#name` token), for any text read
    as a file from its first line: every byte of a token that is code must stand unchanged
    in the view, and where the view has one reading, every byte of a comment and of a
    closed literal's text must be blank. One seed runs the comparison for every character
    past ASCII, so the view's tables cannot fall behind the lexer's unseen. Unit tests hold
    its rules with what the compiler does (rustc 1.99.1, editions 2015 to 2024). The corpus
    has 35 cases: `evidence/rust-code-view-20261114` holds both hiding lines before a
    fetch, a spawn and an `unsafe` block (seven items, all expected; the published v0.8.3
    binary misses four of them), so evidence precision is 28 of 29 (was 21 of 22) and
    recall 28 of 35 (was 21 of 28), with 11 declared as before.
  - *What changes for a reader of `rank.v0`.* Rust code that was hidden is evidence now, so
    a file's score can be higher than it was, and no file's score is lower. A file's place
    in the ranking can fall, because another file's score rose (measured: of two files in
    one patch, the one 0.8.3 ranks first is second here, behind a file whose two hidden
    calls are found now). Three things 0.8.3 missed are found: code after a nested block
    comment, code after a character literal with a long
    escape, and code after `'r#r"\"` written for editions 2021 and 2024 (0.8.3 read that
    form as editions 2015 and 2018 do, and still does in its reading, so code after the
    older form is found as before). For the patch of each of this repository's last 150
    commits (375 Rust files among 1,067) the output is the same byte for byte. Rust lines
    are read twice: two megabytes of ordinary Rust added as one hunk rank in 0.16 s where
    0.8.3 takes 0.12 s, with the same peak memory.
  - *The Rust API of the crates.* Nothing public changes or goes, and what is added cannot
    break a caller (`Evidence`, `Assessment` and every released function keep their shape).
    `deep-diff-forge-graph` gains `HunkLabels`, the evidence labels of a file's hunks with
    the hunks of a created file read as one text (`new` for hunks asked for in file order,
    `naming` for hunks asked for in any order, `of`). Fourteen more items are public only
    for this workspace's own crates, tests and fuzz targets; they are hidden from the
    documentation, are not part of the API and may change: `HunkLabels::scans`,
    `HunkLabels::rule_evaluations`, `HunkLabels::views_alive_at_most`,
    `HunkLabels::entries_kept`, `HunkLabels::carried_bytes` and `HunkLabels::read_together`
    (what a reader has scanned, asked, kept and carried, and how many hunks it reads
    together); `file_evidence_released` (for each item of `file_evidence`, whether the
    reading of 0.8.3 finds it); in `lexical`, `rust_lexer_view` with its state
    `RustLexerState`; and, for the one carried reading of a patch (next entry),
    `CarriedShares` (with its methods `of` and `read_together`), `HunkLabels::in_patch`,
    `RankedFile::scored_in_patch` and `assess_file_in_patch` (a file read with its share of
    its patch, which the rank, the cluster and the daemon's views use) and
    `carried_bytes_on_this_thread` (what the tests that hold a request's carried reading
    count with). `file_evidence`, `assess_file`, `score_file`, `RankedFile::scored` and
    `HunkLabels::new` and `naming` take one file and read it as the only file of its patch
    (their documentation says so): a creation has the whole carried reading there, where in
    a patch it has its share, so for a creation late in a large patch one of them can find
    more than the rank of that patch lists. `hunk_signals` answers as it did: for the hunk
    it is given, read alone (with what the second reading of Rust finds), needing no other
    hunk of the file.
  - *Not closed.* A hunk is a fragment, and both readings start it as code. From a start
    that is not known (a block comment or a string opened above the hunk, in another hunk
    or in unchanged text the patch does not show), the readings are 0.8.3's and the
    lexer's, and code that neither shows is not found. A shebang first line, which the
    compiler skips, is read as Rust by both. `cr"\"` is read by both as a raw C string, as
    editions 2021 and 2024 read it; before 2021 it is the name `cr` and an ordinary string,
    and code hidden by that difference is not found, as in 0.8.3. And the reading of 0.8.3
    keeps what it wrongly takes for code (text in a nested comment, or after a long escape,
    that it reads as code is reported, as it was): a false positive a reviewer sees.

    As everywhere in the lexical scan, no evidence means no token was found, never that a
    change is safe.

- **In a file the patch creates, code after a block comment or a string that an earlier hunk
  had opened was hidden** (found 2026-11-14; reproduced on the published v0.8.3 binary). Every
  hunk was read alone and started as code. But a section that creates a file can be written
  as several hunks, and then what one hunk leaves open is open in the next.
  - *What was hidden.* A file the patch creates, written as two hunks: the first ends with
    `/*`, the second is `// */ pub fn evil() { std::process::Command::new("sh")… }`. Plain
    `git apply` (2.56.0, no option) accepts `@@ -0,0 +1,2 @@` followed by `@@ -2,0 +3,2 @@`
    and writes the lines in order, and the compiler compiles the function. Read alone, the
    second hunk is a line comment. Measured on the published v0.8.3 binary: score 4 with no
    evidence. It holds in every language here that has block comments or strings over lines,
    not only in Rust.
  - *Since when.* Every release that has code evidence, 0.5.0 to 0.8.3.
  - *The fix: one join, for a file the patch creates.* Every hunk of a section that creates a
    file is also read as one text, in the order of the patch: a later hunk is read once more
    from what the hunks before it left open, when that is something. One state is carried:
    in Rust the lexer reading's, which for a created file is the compiler's reading of the
    whole file, and in the other languages their one reading's. The bound is for the whole
    patch: its created files share one carried reading of 256 KiB of new side (each line
    counted with its end) in patch order, and each is read together from its first hunk up
    to the hunk that would take it past what the files before it left, or that has a line
    longer than 512 bytes; from that hunk on, each hunk is read alone, as in 0.8.3 (a file
    with fewer than two hunks read together is not read as one text, and takes nothing).
    This is no defence against a patch's author who means to hide code this way: one line
    longer than 512 bytes in the hunk with the hidden code or any hunk of the file before it,
    or earlier created files, or the file's own earlier hunks, that use up the 256 KiB, turn
    the join off at no cost to the author (reviews reproduced all three). Code that an
    earlier hunk's open comment or string hides is then found only where its hunk read alone
    shows it: each hunk is read alone, as 0.8.3 reads it, with the second reading of Rust
    beside it. The answer is not 0.8.3's for all that: in Rust the second reading still
    reads every hunk and can find more (a review measured a creation at 4 with `new_file` on
    0.8.3 and 7 with `network_fetch` added here; the spawn the earlier hunk hid was found by
    neither). The join closes the case for patches that honest tools write within the bound;
    `git diff` writes a creation as one hunk.
    Where that is depends on the patch alone, so a hunk has the same labels in the rank,
    the cluster with any number of workers, the outline page by page, the hunks by path and
    by address in any order, and asked for alone, and one request reads at most 256 KiB in
    the carried reading in all, whatever it asks. It is a further reading,
    never a replacement: every hunk is still read alone, exactly as before, so here too no
    score is lower than 0.8.3's and no signal or listed item of the ranking is missing (and
    at the bound of a file's printed list what only the carried reading finds is listed
    after the items of 0.8.3, like what only the lexer reading finds). What plain Git does
    with a later hunk of such a section: at an old position of 0 or 1 it refuses the patch,
    and at any other it puts the hunk after the one before, whatever the number says. The
    section is read as one text either way: reading together what Git refuses can add a
    finding and takes none away.
  - *How it is held.* Unit tests hold the creation in several hunks (comment, string and raw
    string openers; false numbers), and that hunks of a file that exists are read each on
    its own. A property test holds, for 4,500 generated files whose hunks have every form
    and any numbers, that no hunk has fewer items than when it is read alone, that only the
    hunks of a creation have more, that a creation's hunks have every item the lexer
    reading finds in the file as one hunk, and that the per-hunk labels are the file's,
    asked in order, backwards, one at a time, or at random with repeats. A rule in the
    `evidence_scan` fuzz target holds the same for a stretch of Rust cut into the hunks of a
    creation at lines the input chooses, and that its hunks are read together as far as the
    bound says, and that the created files of a patch (the same creation two to five times, at
    paths in several languages) share it in patch order; two of its seeds pass the bound
    across Python, TypeScript, Go, shell, YAML and Rust. Unit tests hold the bound: on
    creations that pass it by their bytes and by one long line, in Rust and in JavaScript,
    every hunk has the same labels in every view and order of asking, and a hunk past the
    bound, the last one asked for alone among them, reads none of the hunks before it. Its
    edges are held exactly (a creation of 256 KiB is read together to its end and one of a
    byte more is not; a line of 512 bytes is carried and one of 513 is not, in ASCII and in
    two-byte characters; the budget used up exactly at a file's end leaves the next file
    nothing, and one byte into the next file cuts it at that hunk, with the budget passing
    into and out of each of Rust, JavaScript, Python, Go, shell and YAML); each of the
    mutations that moves either limit by one, makes a `>` a `>=`, counts characters for
    bytes, gives each file the whole budget again, shares it among the Rust files alone or
    the Rust and JavaScript files alone, or reads a file of a patch with its own budget in
    the rank, the cluster or a view, fails them. A further unit test compares the shares of
    240 generated patches of 1 to 60 files with a model written from the rule as stated here,
    and the rank's carried bytes with the model's: creations from one line to past the budget,
    lines over 512 bytes in any hunk, every language by extension, by name and by shebang,
    files in none, files that exist, renamed, deleted and binary files, and more than 25
    creations. Leaving a share under 200 bytes, a file known by its shebang, a `Dockerfile` or
    a `Makefile` uncharged, or giving the budget again from the 25th created file, fails it.
    Counted for whole requests: the bytes the carried reading reads are counted on the thread,
    whatever readers a request makes, and on patches of many creations, each under every limit
    of a file of its own, the rank, the outline whole and page by page, every hunk whole and
    page by page, the hunks by path, by address in several orders and each alone, and the last
    hunk of each file read at most 256 KiB each; the outline and the listing of every hunk
    read it once, as the rank does.
  - *What it costs, stated for any patch and held by tests that count.* The unit is a scan of
    a line: a view of a line is made by scanning the line once for each reading the view
    unites.
    - *The views of a line, for each side it is on.* The view of 0.8.3, made as 0.8.3 made
      it: one scan for each reading its state holds and one more for each of them that
      carries a string, eight at most. For Rust, the lexer view: five scans at most (four
      readings that each resume a literal, and one scan that resumes none; readings that
      begin from the same place share a scan). And for a later hunk of a creation that came
      into something open, the carried view: five scans at most for Rust and eight for the
      other languages (readings that begin the same as code share a scan). For JavaScript
      "something open" includes the last code byte of the line before, which decides whether
      a `/` begins a regex, so there nearly every later hunk of a creation has a carried
      view.
    - *So, for each side a line is on.* In a file that exists, or a creation in one hunk:
      at most 8 scans, and 13 for Rust, where 0.8.3 made at most 8; for ordinary text 1, and
      2 for Rust, where 0.8.3 made 1. In a later hunk of a creation: at most 5 more for
      Rust and 8 more for the other languages; for ordinary text 1 more, and none where the
      hunks before left nothing open. A scan leaves the state the next hunk goes on from, so
      no line is read only to pass a state on. A hunk of a creation asked for by itself
      costs the hunks before it that are read together, once (one view a line), and then its
      own views; a hunk past its file's share costs its own views only, as in 0.8.3. The one
      budget of a patch keeps that a small constant for a whole request, whatever the patch
      and whatever is asked: one request (a ranking, an outline page, any hunks in any order,
      one hunk) reads at most 256 KiB of lines of at most 512 bytes in the carried reading in
      all (the most measured: lines that are each one JavaScript word). The outline and the
      listing of every hunk take the labels of a creation from the ranking's reading, so they
      read it once. An MCP view whose answer is over its byte bound once escaped is asked
      again with a smaller page, at most eight times in all, as in 0.8.3; each of those runs
      is such a request. So one MCP view call takes up to eight times one view's time, and the
      factors stated below for a view apply to each of its runs: a review measured one
      `review_outline` call on a 64 MB patch, part JavaScript and part Rust, made to run eight
      times, at 34 s against 25 s on 0.8.3. MCP over stdio has no deadline of DDF's own (the
      30 s is the socket client's).
    - *The rules.* The rules of a signal are asked in their order until one finds something,
      as in 0.8.3, so no rule is asked of the first view that 0.8.3 did not ask; a signal
      that is found is not asked for again in a further view.
    - *Memory.* The two new views (the lexer's and the carried one) are each made, read by
      the rules and dropped before the next view is made, and the readings inside each are
      united one at a time, at one bit a byte. The view of 0.8.3 keeps one string for each
      of its scans until it has united them, as in 0.8.3. A reader keeps one state for a
      creation read in file order, whatever the number of its hunks, and the labels of the
      hunks a listing by address names, eight bytes each. Each item found costs about 120
      bytes, as in 0.8.3. The import rule no longer keeps a list of every keyword on a line
      (24 bytes each in 0.8.3). The figures below are measured peak memory, which the
      counters do not prove.
    - *Held by tests that count*: the scans of each line against these bounds (2,000
      generated files of every shape, all read, and the shape that cost the most in review)
      and exactly for ordinary text; the views made here that are alive at once (never more
      than one); the rules asked (the rules after the one that finds are not asked); the
      entries kept; the bytes the carried reading reads, counted for a whole request across
      every file it reads (256 KiB at most in a request); and the import rule against the one
      that kept a list (40,000 lines).

    outline and the hunks view label the hunks of a creation as the rank does.

    lines only, which plain Git appends to the file after the hunk that ended it, whatever
    its number says; chains of those two; removal hunks that Git can only apply in reverse
    file order (a deletion or a file's tail written as several hunks); hunks listed out of
    the file's order; and hunks placed by `git apply --unidiff-zero`, `--allow-overlap` or

    hunks inside a line). Besides: a path named by more than one section is read section

    two section shapes that Git can apply in order: see the third Security entry above), and
    a hunk with unseen
    lines above it is started as
    code, whatever is open there. And a creation is read together only up to its share of
    the patch's bound: from the hunk that would take the reading past what is left of the

### Changed

- `PatchParseError` has a new variant, `PathInSeveralSections { line_number, path,
  same_section }` (the enum is `#[non_exhaustive]`); `same_section` is `true` for a single
  section that renames a path to itself, which is refused as well, and its message names
  that section rather than an earlier one (review of 0.8.4, R84-L-5). `SectionWithoutPatch`
  now also covers a Git section with headers but no change in them, and `InconsistentHeader`
  a traditional diff with `/dev/null` on both sides; their messages say so.
- **`deploy release` and `--help` no longer claim GitHub** (review of 0.8.4, R84-L-3). The
  `deep-diff-forge.release.v0` schema, its members and the target names are unchanged; only
  values change. `github` and `github-release` are `skipped` (were `published` and
  `blocked`), the targets `gitea` and `forgejo` are added as `published` beside `gitlab`, and
  a skipped target is not listed in `pending`, which is now `["crates.io"]` (was
  `["github-release", "crates.io"]`). `--help` says a release is a signed tag on GitLab, Gitea
  and Forgejo and a local release, and that nothing goes to GitHub.
- **Built and published without GitHub.** `scripts/release_local.sh` builds a release on the
  owner's machine (two fresh exports, `release.yml`'s cargo command, one SHA-256 required;
  the smoke, glibc check, SBOM, archive, receipt and `SHA256SUMS`) and verifies one (the tag's
  signature, the checksums and their signature, a rebuild, against the new
  `.github/release_allowed_signers`), with a self-test,
  `scripts/test_release_local.sh`, and the recipes `just release-local-build`,
  `release-local-verify` and `release-local-test`; `verify` refuses an archive whose members
  are not exactly the five it packs (review of 0.8.4, R84B-L-2: a second member `./D/…` was
  what `tar -xzf` left). `just release-tag` pushes the tag to GitLab, Gitea and Forgejo only,
  refuses a remote whose URL names github.com, and refuses to tag when `git status --porcelain`
  prints anything before the release gate or after it, so a tracked change or an untracked file
  Git does not ignore stops it (review of 0.8.4, VR84B-M-2: the check was `git diff --quiet`,
  which does not see an untracked `build.rs` that Cargo reads). It does not see ignored files,
  or files hidden by `status.showUntrackedFiles=no`, and it does not compare `HEAD` before and
  after the gate, so it does not prove the tag names the gated commit: the release relies on a
  dedicated, freshly cloned worktree under exclusive control, with no ignored files and a stable
  `HEAD` ([Tag And Push](../RELEASE_AND_PUBLICATION.md#tag-and-push); VR84C-M-1,
  VR84C-M-2). The advisories
  are in the repository: [DDF-2026-001](../advisories/DDF-2026-001.md) (G1, G2) and
  [DDF-2026-002](../advisories/DDF-2026-002.md) (the Rust code view). Security reports go
  to a confidential issue on GitLab ([SECURITY.md](../../SECURITY.md#reporting-a-vulnerability))
  instead of a private GitHub advisory.

### Fixed

- **The Git differential applies patches for real.** `git apply --numstat` and `--summary`
  read a patch but do not say what an apply writes, so content taken from the object store
  and Git's order of removals and creations were never in play (`--numstat` even lists an
  `index`-only section that a real apply refuses). `tests/git_differential.rs` now has a
  `real_apply` module: each case is applied in a scratch repository whose object store holds
  the blobs the patch names, and the tree Git leaves is compared with the tree the review's
  sections describe (path, type, executable bit and content). It covers each finding above,
  the shapes that stay reviewed, and patches written by Git itself (a change of type, a copy
  of a changed file, a three-commit series on one file). Control: the tests of the findings
  fail on the v0.8.3 parser.
